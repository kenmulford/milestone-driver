# Not-buildable handling: solve-milestone reference

Loaded by core `SKILL.md`'s `### 4. Loop over issues in dependency-graph order` **only for an issue the buildability check just failed** — triage-parked, live-label park, or a dependency not yet merged. A run in which every issue is buildable never reads it. Both modes share it: parallel mode's parallelizable-set selection excludes these issues from dispatch but does not label or comment them. Missing or unreadable once an issue has failed the check is a **systemic failure** (core `SKILL.md`'s `## Autonomy`).

---

- **Triage-parked or prior-run park** (`issueStates[n].blockers == true` OR live labels include a blocker label): no build attempt. That label is normally already there (Phase 0 or a prior run); a Phase 0 application interrupted by a transient `gh` error leaves it absent, so check live — `gh issue view <n> --json labels --jq '[.labels[].name]'` — and if none of `needs design`, `needs decision`, `blocked` is present, apply `issueStates[n].label` now via the apply-time label helper (`gh label create … --force` + `gh issue edit <n> --add-label …`). Apply `in progress` (same helper) if a feature branch for this issue exists with commits (`git branch -a`). Under a held **Auto** answer, a `needs design`/`needs decision` park still unattempted this run enters the `## The Auto loop` in `${CLAUDE_PLUGIN_ROOT}/skills/remediate-handoff.md` first; clean re-triage → label cleared, the issue rejoins the buildable set this pass. Otherwise, note the issue in the run output (label + blocker reason) and continue.

  > **One blocker label per issue.** A parked issue carries exactly ONE blocker label. Do not apply `blocked` to an issue that already carries `needs design` or `needs decision` — the triage/design label is the root block and takes precedence. (`in progress` is orthogonal and may still be applied.)

- **Dependency not yet merged** (condition (a) fails, (b) and (c) pass): apply `blocked` (and `in progress` if a branch with commits exists) via the apply-time helper, and post a comment in the blocked-comment shape (`skills/output-style.md` — reason · evidence · what unblocks it, the evidence slot being this issue's OWN unmerged upstream numbers) with the opener byte-unchanged:
  `gh issue comment <n> --body "🔴 Blocked — dependency-ordering hold; no design or decision work is needed for this issue itself. Evidence: unmerged upstream(s) #<each unmerged issue in edges[\"<n>\"]>. Unblocks: merge the upstream(s) and clear any upstream parks, then remove this \`blocked\` label and re-run solve-milestone to build this issue."`
  Then hold every transitive dependent (any issue whose `dependencyGraph.edges` include this issue or another held issue): for EACH such issue m, **before applying `blocked`**, check m's live labels (`gh issue view <m> --json labels --jq '[.labels[].name]'`). Already carrying `needs design`, `needs decision`, or `blocked` → do NOT add another. Otherwise apply `blocked` (+ `in progress` if it has a branch). Either way post the same KIND of comment, naming m's OWN unmerged upstream(s) from `edges["<m>"]` rather than this issue's (same wording: dependency-ordering hold, clear `blocked` and re-run). Note all held issues in the run output; continue with independent buildable issues.
