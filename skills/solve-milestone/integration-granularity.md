# Integration granularity — solve-milestone reference

Loaded when the profile resolved `integrationGranularity` to **`"wave"`** or **`"milestone"`**, by whichever mode file is running — `parallel-waves.md` or `sequential-loop.md`; both value sections below serve both execution modes. Under the `"issue"` default this file is **never read**, and every step of `parallel-waves.md` and of the sequential loop runs exactly as written there. It holds those two values' own mechanics plus the **per-step deltas** they apply to `parallel-waves.md`'s Phase 1 and Phase 2. **Missing or unreadable** once granularity has resolved to `"wave"` or `"milestone"` is a **systemic failure** — surface it and halt the run per core `SKILL.md`'s `## Autonomy` → "Systemic failures that halt the run", the same class as a missing `parallel-waves.md`. Do **not** silently degrade to `"issue"`.

A run that resolved `integrationGranularity: "milestone"` additionally loads `milestone-granularity.md`, which owns that value's branch model and fold mechanics; this file never restates them and points at them instead. A `"wave"` run reads it only at the anchors this file and `skills/solve-issue/wave-clauses.md` cite.

## `"wave"`

The merge-tail **MECHANISM is unchanged** (merge-in + re-verify against accumulated state + bounded auto-resolve, #73); only the **target** and **PR-opening** differ:

- **No per-issue PR.** Phase 1's per-issue tail (step 8) builds, verifies, commits, and pushes each issue branch but opens **no per-issue PR**: `solve-issue` step 6.6 is granularity-conditional, and wave granularity is one of the values that suppresses it. The wave-state entry for such an issue carries `pr: null`.
- **Integrate into a wave branch.** Integrate the Wave's built-green **logic** branches into a **wave branch** `wave/<milestone>-w<N>` (N = the Wave number). **Create the wave branch fresh and idempotently:** unlike the per-issue `issue/<n>-<slug>` branches — which may carry **unpushed** commits Phase 1's pre-clean guard must preserve-don't-clobber (`parallel-waves.md` step 2) — the wave branch is a **regenerable integration artifact** assembled entirely from already-pushed per-issue logic branches, so it is **safe to force-clear and rebuild** on every run. Before creating it, delete any stale leftover from an interrupted prior run (`git branch -D wave/<milestone>-w<N>` locally; `git push origin --delete wave/<milestone>-w<N>` if it was pushed) and recreate it fresh from the current `integrationBranch` tip. Then apply the **#73 policy unchanged**: merge each branch into the wave branch, re-verify against accumulated state (unit + deferred E2E / port-binding gates), bounded auto-resolve on conflict, else park `blocked` (label + comment + preserve branch) and continue with the next branch. The integration target is the wave branch, so siblings are re-verified against each other exactly as in the per-issue tail.
- **One wave PR.** Open **one wave PR** → `integrationBranch` whose body lists the Wave's logic issues in the wave-PR-body shape (`skills/output-style.md`): one line per logic issue, its **evidence slot** naming that issue's branch and the gates it passed on the wave branch (an issue listed with no branch or gate record is an unfilled slot), plus the `## Code Review` section that shape requires — without it `hooks/code-review-gate.sh` denies both the `gh pr create` and the squash-merge below. On **CI green**, **squash-merge** the wave PR. A repo with **no required checks (no CI)** is **vacuously green** — squash-merge immediately, as the per-issue path does (with no required status checks to gate on, `gh pr merge --squash` is mergeable; the behavior the per-issue auto-merge relies on, `solve-issue` step 8). Auto-merge-on-green moves from per-issue to **per-wave**.
- **Explicit issue close (do NOT rely on the `Closes #…` keyword).** A GitHub `Closes #n` keyword auto-closes an issue only when the PR merges into the repository's **default** branch. The wave PR targets `integrationBranch`, typically **not** the default branch (e.g. `develop` vs `main`), so the keyword would **not** fire. After the wave PR squash-merges, the **orchestrator explicitly closes the Wave's logic issues** one call each — `for n in <each issue number>; do gh issue close "$n" --reason completed; done`, the numbers carrying no `#` prefix. The loop form is required (`skills/solve-milestone/milestone-granularity.md (Close every issue on the branch)`). A failed close logs one line and the loop continues to the next issue; **every issue that failed to close is then named in the final summary's `🔴 Your move:` section**, taking the milestone PR's red-CI shape (`skills/solve-milestone/milestone-granularity.md (Emit one 🔴 line)`). If `integrations.trello` is present and a card handle was resolved, tick the checklist items for all logic issues just closed per `trello-sync.md § Wave granularity` (under `## Loop hooks`; best-effort per item; failure logged, loop continues). The wave PR body may still list the issues for traceability, but the close is the explicit `gh issue close` step, never the keyword.
- **Wave-branch disposition + re-sync.** After the wave PR squash-merges, **delete the wave branch** (`gh pr merge --squash --delete-branch`, plus `git branch -D wave/<milestone>-w<N>` locally if a local copy remains) and **re-sync the local `integrationBranch`** (`git fetch`, fast-forward) **before the next Wave** — consistent with the per-issue tail's `--delete-branch` + re-sync (`parallel-waves.md` Phase 2 step 2).

**Logic-only carve-out.** The Layer-2 visual gate is per-UI-issue, so a single wave PR cannot both auto-merge (logic) and hold open (UI). A Wave containing UI issues keeps those **per-issue / held**: each UI issue gets its own PR with the `needs review` label at Phase 1 step 8 (issue-granularity handling for that issue, held open for human visual sign-off), and **only the logic issues join the wave branch**. The wave PR's explicit-close list scopes **only the logic issues that actually joined the wave branch** — never the held UI issues.

**All-UI wave.** A Wave whose **entire** built-green set is UI issues opens **no wave branch and no wave PR** — every issue is held per-issue for visual sign-off, and there is nothing to integrate at the wave level.

**Trade-off.** **One red wave-PR CI blocks the whole Wave** — acceptable because the strong local gates (unit + static preflight + `/code-review` + the tail's re-verify) catch most failures **before** CI; CI is the backstop. **Not** for repos with weak local gates.

## `"milestone"`

The merge-tail **MECHANISM is unchanged** (merge-in + re-verify against accumulated state + bounded auto-resolve, #73); only the **target**, the **on-green action**, and the level the **visual gate** sits at differ. The mechanics are `milestone-granularity.md`'s and are **not** restated here or in core `SKILL.md`; this section is the pointer:

- **Nothing is pushed, and no per-issue PR is opened for any issue, UI included.** Phase 1 builds, verifies, and commits on `issue/<n>-<slug>` branches cut from the milestone branch `milestone-<number>-<slug>`; Phase 2 folds each built-green branch onto that branch with the local squash-merge-plus-one-commit of `milestone-granularity.md § Folding an issue into the milestone branch`, whose `Issue: #<n>` trailer answers every resume and buildability read (`§ Resume and buildability from the trailer`). The same two sections serve the sequential loop's local merge, so nothing here is parallel-mode-exclusive.
- **One push, one PR, one CI run at milestone end** (#371), and the per-issue visual gate collapses into that PR's `visualHold` decision (#376, `docs/profile-schema.md (Should the single milestone PR wait)`) rather than a `needs review` label on a per-issue PR that never exists.

## Phase 1 deltas

Each row names a site in `parallel-waves.md § Parallel mode — Phase 1: concurrent stage dispatch` and the delta the resolved value applies there. Every other instruction at that site is unchanged.

| Site | Value | Delta |
|---|---|---|
| `### Parallelizable-set selection`, buildable condition (a) | `"milestone"` | A dependency counts as satisfied when it carries its `Issue: #<n>` trailer on the milestone branch, **not** when it is merged to `integrationBranch` — nothing merges there before milestone end (`milestone-granularity.md § Resume and buildability from the trailer`). |
| Phase 1 / Phase 2 summary bullets; step 11's held set | `"milestone"` | The green set is held **built only, nothing pushed and no per-issue PR**, instead of built + pushed. Phase 1 performs no merge to the milestone branch either — that is the target Phase 2 folds onto. |
| Wave-loop preamble, Wave-boundary barrier | `"milestone"` | Phase 2's squash-merges land on the **milestone branch**; the local `integrationBranch` re-sync is a **no-op**, nothing having been pushed. |
| Step 2, `<base>` | `"milestone"` | `<base>` is the milestone branch `milestone-<number>-<slug>` (`milestone-granularity.md § Branch model`), not `integrationBranch`. |
| Step 2, pre-clean guard | `"milestone"` | **The marker is integrated-or-not, not pushed-or-not.** The `origin` confirmation drops as unsatisfiable, nothing being pushed; "not yet merged" / "already merged" read off the `Issue: #<n>` trailer on the milestone branch (`milestone-granularity.md § Resume and buildability from the trailer`); **"already pushed" is not a discard-safe condition at all**, no issue branch ever being pushed. The branch safe to discard is the one whose trailer is already on the milestone branch. |
| Step 8, `solve-issue` steps 6.2 to 6.6 | `"wave"`, `"milestone"` | Those steps are granularity-conditional: the version bump, the commit, and the push / PR-open inherit their own conditionals — wave granularity suppresses the per-issue PR (step 6.6); milestone granularity suppresses the push and the PR both. |
| Step 9, checkpoint freshness, `pr` leg | `"milestone"` | **No issue has a per-issue PR, UI included**, so every entry takes the `pr`-absent branch and is compared with `branch_epoch` from `for-each-ref`. |
| Step 9, probe path a | `"milestone"` | Path a matches nothing for **every** issue — that granularity's normal state, and never "nothing built". Path b and the trailer carry the signal there. |
| Step 9, `isUI` derivation | `"milestone"` | `<base>` is the milestone branch, **never** `integrationBranch`: a branch cut from the milestone branch and diffed three-dot against `integrationBranch` reports every already-folded issue's files as this issue's own. |
| Step 9, `built-green` | `"milestone"` | Ground truth is instead a **local** branch with commits ahead of the milestone branch, **or** its `Issue: #<n>` trailer already there — neither an open PR nor a pushed branch ever exists, so the `ls-remote` push confirmation does not apply. |
| Step 9, `abandoned` legs | `"milestone"` | The legs resolve to **0 commits ahead of the milestone branch** (path b), **no `Issue: #<n>` trailer on that branch**, and **no park label**. The trailer leg is load-bearing: an already-folded issue whose worktree step 2 recreated fresh sits at 0 commits ahead with a clean worktree and would otherwise match `built-green` and `abandoned` at once. |
| Step 9, wave-state `pr` field | `"wave"`, `"milestone"` | `pr` is `null` for a `built-green` **logic** entry under wave granularity, and for **any** entry under milestone granularity, UI included (no per-issue PR by design). `branch` stays the freshness anchor in both. |
| Step 10, cleanup basis | `"milestone"` | **The basis is local and the removal behavior is unchanged:** an integrated branch's work lives in its squash commit on the milestone branch (`milestone-granularity.md § Folding an issue into the milestone branch`), and a built-green branch not yet folded keeps its commits — `git worktree remove` deletes the checkout directory, not the branch — so step 2's carries-work leg resumes them next run. |
| Blast-radius boundary | `"milestone"` | The immediate target is the milestone branch, which reaches `integrationBranch` only through the single milestone-end PR (`milestone-granularity.md`). `protectedBranch` is untouched either way. |

## Phase 2 deltas

Each row names a site in `parallel-waves.md § Parallel mode — Phase 2: serial verified merge tail`.

| Site | Value | Delta |
|---|---|---|
| Preamble, which branches integrate | `"milestone"` | **The tail integrates every built-green branch, UI included.** No per-issue PR exists for the visual hold to attach to, so a UI branch excluded here would have no integration path at all; the hold moves up one level to the single milestone PR's `visualHold` gate (#376, `docs/profile-schema.md (Should the single milestone PR wait)`). |
| Run order | `"milestone"` | Ascending-issue order over **every** built-green branch, UI included. |
| Step 1, `<target>` | `"wave"` | `<target>` is the **wave branch** (#75), not `integrationBranch`. |
| Step 1, `<target>` and where the fold runs | `"milestone"` | `<target>` is the **milestone branch**, and the fold runs **there** rather than onto the issue branch, per `milestone-granularity.md § Folding an issue into the milestone branch`. That file owns the mechanics — squash-merge the issue branch onto the target, re-verify against the staged state, commit with the `Issue: #<n>` trailer — and they are not restated here; steps 2 to 4 read against it. |
| Step 2, coherence pass | `"wave"` | **Run the read-only post-build coherence pass here too** (`coherenceReviewAgent`, present-and-configured-or-silently-skipped, never-gating): the assembled wave is the largest body reviewed before its one wave PR, the wave-granularity analogue of `solve-issue` section 6's per-issue pass. |
| Step 2, on green | `"milestone"` | **The push, the `gh pr merge --squash --delete-branch`, and the re-sync do not run, unconditionally** — no profile key and no conditional enables any of them, nothing reaching origin before milestone end (`milestone-granularity.md § Branch model`). Integrate instead with the local squash-merge-plus-one-commit that file defines, whose `Issue: #<n>` trailer every buildability and resume read resolves against. The wave-granularity coherence clause **does not** carry over: the largest body reviewed before one PR is the whole milestone, so that analogue belongs to the milestone-end sequence (#371). |
| Step 3, conflict park recovery | `"milestone"` | **The park is identical but the recovery command is not.** `git merge --squash` writes no `MERGE_HEAD`, so `git merge --abort` fails there with `fatal: There is no merge to abort (MERGE_HEAD missing).` The recovery is `git restore --staged --worktree .`, run on **both** park paths (step 4 included) before the next branch, per `milestone-granularity.md § Folding an issue into the milestone branch`. Do not substitute `git reset --hard`, which consumer destructive-command hooks routinely block by pattern. |
| Wave-boundary notification | `"milestone"` | The Wave completes when **every** built-green branch is folded onto the milestone branch, UI included, and **no** per-issue PR is held. X counts every built-green issue squash-merged onto the milestone branch, UI included. |
