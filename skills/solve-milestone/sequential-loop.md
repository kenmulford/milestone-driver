# Sequential loop: solve-milestone reference

Loaded by solve-milestone when the run resolves to **sequential** mode (the *Resolve execution mode* Before-starting step), via the mode branch point in core `SKILL.md`'s `### 4. Loop over issues in dependency-graph order`. It holds the per-issue build steps that run for an issue the loop found **buildable**; buildability itself, the not-buildable branch, and both branch points stay in core `SKILL.md`. In **parallel** mode this file is **never read** — `parallel-waves.md`'s Wave loop replaces these steps. **Missing or unreadable** once the mode has resolved to sequential is a **systemic failure**: surface it and halt the run per core `SKILL.md`'s `## Autonomy` → "Systemic failures that halt the run".

---

For each buildable issue, in dependency-graph order:

1. Ensure the local build target is current: `integrationBranch` (`git fetch`, fast-forward), or, under `integrationGranularity: "milestone"`, the milestone branch, which is already current because nothing is pushed and each fold committed locally.
2. **Run `solve-issue <n>` on this main line, in-thread, never as a dispatched agent.** `solve-issue` dispatches an implementer and a review fan-out, so running the pipeline inside a dispatched agent would sit both at depth 2, where a completion notification never arrives and the issue strands mid-pipeline with work uncommitted and no park signal (`docs/architecture.md` → `## Dispatch topology`); the orchestrator runs the pipeline itself and dispatches those agents as leaves. The `--async` token is retired and inert (`skills/solve-issue/async-mode.md`).

   **Restate both held values inline when invoking, with ACTUAL VALUES:** the Phase 0 triage result for step 0 (e.g. "step-0 result for #N: { blockers: false, label: null, advisories: [...], risk: light }, edges: [...]") so step 0's Branch A reuses it instead of re-invoking triage, and the target version for step 6.4's milestone-run path (e.g. `targetVersion: <x.y.z>`). If either is no longer reliably in context (long run, context compression), step 0 falls to Branch B (fresh single-issue triage), and step 6.4 **re-derives** the target version from the milestone rather than asking (`skills/solve-issue/SKILL.md` step 6.4, standalone bullet). Neither prompts.

   The **background-dispatch permission decision already resolved at run start** (the *Resolve execution mode* Before-starting step, row 2 — the permission pre-flight gate ran there; do NOT re-run it) still governs the leaves `solve-issue` dispatches from here: a gap makes those dispatches synchronous for this run.

   **Operator redirect window.** Between issues the main line is interactive, so the operator can redirect before the next issue begins. **SendMessage addressing:** the main line CAN send a dispatched leaf a mid-run message (delivered at its next tool-use round, not instantaneously) — but only by that leaf's own dispatched ID/name; an agent-TYPE name (e.g. `milestone-driver:implementer`) is not a reachable address, and only the session that spawned the leaf can message it. **Dispatched leaves never call PushNotification** — confirmed absent from subagent tool registries (see issue #97 recorded decision); the main line emits at this boundary.

   After each issue completes, post the chunk-boundary board first (Template 2, core `SKILL.md` `## Output spec`), then emit a `PushNotification` for the terminal state of the just-completed issue (parallel mode emits its parks at `parallel-waves.md`'s Phase 1 step 9 instead):
   - **Issue parked** (any park subtype — triage-park, dependency-hold, STOP/build-park): emit `⏸️ #N parked — <reason>` (where `<reason>` is the park label + brief blocker description, e.g. "needs decision: new dependency").
   - **Issue completed** (merged or held for visual review): no per-issue notification here — the 🏁 run-complete notification (emitted after the Final summary) is the aggregate end signal.

3. **Park-and-continue on STOP/PAUSE:** If `/milestone-driver:solve-issue` returns a STOP or PAUSE (no root cause, new dependency, architecture conflict, scope overrun, ambiguity, unmet gate), **park the issue and continue** — do **not** halt the loop. Parking steps:
   a. Apply the appropriate label using the apply-time label helper (`needs decision` for a new dependency or architecture call; `needs design` for a design/spec gap; `blocked` for an unresolvable unmet gate).
   b. Apply `in progress` if a branch exists with commits.
   c. The STOP/PAUSE reason is already recorded on the issue (by `solve-issue` or the implementer). Confirm it is there **and that it fills all three slots of the park-comment shape** (`skills/output-style.md`) — reason · evidence · what unblocks it; if it is missing, or is present but carries no evidence slot, post it (or the missing slot) via `gh issue comment <n>`.
   d. Leave the issue open; note it in the run output.
   e. Continue to the next issue in the dependency graph whose dependencies are merged.
4. **On success**, `/milestone-driver:solve-issue` has reached one of two terminal states: for a **non-UI issue** it has squash-merged to `integrationBranch` and closed the issue; for a **UI issue** held at the visual-review gate (`solve-issue` steps 6.7–6.9) it has left the PR **open** with the `needs review` label, issue not closed, for human visual sign-off. For non-UI merged issues, if `integrations.trello` is present and a card handle was resolved, tick the checklist item for issue `#<n>` per `trello-sync.md § Issue granularity` (under `## Loop hooks`; best-effort; failure logged, loop continues). Re-sync the local build target before the next issue either way (step 1); for a UI issue nothing was merged, so it is a no-op.
   - **Milestone granularity: fold first, then re-sync.** There is no terminal state above to observe: `solve-issue` opened no PR, merged nothing, held no UI issue, and closed nothing (`skills/solve-issue/SKILL.md (Resolved from the profile at step)`). This loop instead squash-merges the completed issue's branch onto the milestone branch and commits it, running the same steps the parallel Phase 2 tail runs, per `milestone-granularity.md § Folding an issue into the milestone branch`; neither caller carries its own copy, and a conflict or red re-verify parks `blocked` there and continues.
   - That commit's `Issue: #<n>` trailer is what buildability condition (a) reads for the next issue (`milestone-granularity.md § Resume and buildability from the trailer`). A parked issue leaves no trailer, so its dependents stay unbuildable this run.
   - **Wave granularity: integrate at the Wave boundary.** The non-UI terminal state above does not hold: nothing merged or closed, so no per-issue Trello tick. The boundary is every issue of the current Wave holding a terminal state (`skills/solve-milestone/SKILL.md (Process issues Wave by Wave)`). Under `integrationGranularity: "wave"`, read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/integration-granularity.md` (missing or unreadable is the systemic failure its opening paragraph declares) and run its `§ "wave"` sequence: wave branch, one wave PR, explicit close, wave-branch delete plus `integrationBranch` re-sync. Both carve-outs hold: `skills/solve-milestone/integration-granularity.md (Logic-only carve-out)` keeps UI issues per-issue and held, and `skills/solve-milestone/integration-granularity.md (All-UI wave)` opens no wave branch and no wave PR.
