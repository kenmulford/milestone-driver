# Parallel waves — solve-milestone reference

Loaded by solve-milestone when the run resolves to parallel mode (the *Resolve execution mode* Before-starting step; the mode branch point sits at the top of core `SKILL.md`'s `### 4. Loop over issues in dependency-graph order`). Holds the parallelizable-set selection and the two-phase concurrent-build-then-serial-merge-tail machinery. **Missing or unreadable** once mode has resolved to parallel is a **systemic failure** — surface it and halt the run per core `SKILL.md`'s `## Autonomy` → "Systemic failures that halt the run". Do **not** silently degrade to sequential, and do not fail with an uninformative crash.

## Contents

Selecting the concurrent set · Phase 1: pipelined build and review · Phase 2: the serial merge tail · Integration granularity (the branch point; values live in `integration-granularity.md`).

---

### Parallelizable-set selection (parallel mode)

**The parallelizable set.** From the issues in the current Wave, an issue belongs to it **iff both** hold:

- it is **buildable this pass** — the three conditions **(a)/(b)/(c)** already defined above (every issue in `dependencyGraph.edges["<n>"]` merged to `integrationBranch`; no live blocker label; `issueStates[n].blockers == false`); **AND**
- it carries **no `dependencyGraph.edges["<n>"]` edge to another issue currently in the same candidate set** (mutual independence).

The set is **buildable ∧ mutually-independent**. Do not re-derive buildability here — it is the (a)/(b)/(c) definition the sequential loop uses; this subsection adds only the intra-set independence guard.

**The intra-set edge check is a guard, not the workhorse.** Two same-Wave issues whose files overlap but share no build dependency correctly stay in the set (triage draws no `DEPENDS_ON` edge); the overlap surfaces at **merge**, where the orchestrator-owned **serial verified merge tail** reconciles it.

### Parallel mode — Phase 1: concurrent stage dispatch

Two phases share this skill's Phase 0 triage and dependency graph:

- **Phase 1** — **pipelined build and review**: each issue's reviewer is dispatched the moment that issue's implementer returns and clears step 6's gates, **not** after the Wave's slowest implementer returns. Builds the parallelizable set in a worktree fleet; **does not integrate**. The green set is assembled at step 9's gather and held for Phase 2.  **Concurrency is by stage, not by issue:** the orchestrator fans out one leaf per issue per stage and is the only session that fans out (`docs/architecture.md` → `## Dispatch topology`).
- **Phase 2** — the **serial verified merge tail**. Integrates the held green set to `integrationBranch` one branch at a time, running the deferred gates (E2E, any server-starting preflight) once against accumulated state. See `### Parallel mode — Phase 2: serial verified merge tail` below.

**Non-default `integrationGranularity` — the branch, stated once.** Every step below is written for the **`"issue"` default**. If the profile resolved `integrationGranularity` to `"wave"` or `"milestone"` at run start, read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/integration-granularity.md` and apply its **`## Phase 1 deltas`** table as you go — it names each affected site below and the delta that value applies there. Under `"issue"` that file is **never read** and every step runs exactly as written. `### Integration granularity (issue vs wave)` below carries the full branch point.

After Phase 0 triage, process the milestone **Wave by Wave** (the sequential loop's Wave order). **Each Wave completes across BOTH phases before the next begins:** Phase 2 runs to completion at Wave end — its squash-merges landing on `integrationBranch`, the local `integrationBranch` re-synced — **before** the next Wave's step 1 cuts its fleet from that target. Call this the **Wave-boundary barrier**. **A Wave has exactly TWO barriers:** this one and **step 9's gather** before it. Pipelining removes only the Stage A → Stage B boundary *inside* Phase 1; Phase 2 stays serial, its cross-issue reconciliation needing every branch present. For each Wave:

1. **Compute the parallelizable set.** Per `### Parallelizable-set selection` above: **buildable ∧ mutually-independent**. An empty set (every Wave issue parked or dependency-held) advances to the next Wave with nothing dispatched.

2. **Create the worktree fleet (orchestrator-owned).** One worktree per set issue in the gitignored scratch dir `.milestone-config/worktrees/`, cut from `<base>` — `integrationBranch`. `<base>` names that branch everywhere below (steps 2 and 5), as `<target>` does in Phase 2:

   ```
   git worktree add .milestone-config/worktrees/issue-<n> -b issue/<n>-<slug> <base>
   ```

   **Pre-clean guard (resume-aware) — the branch.** A leftover `.milestone-config/worktrees/issue-<n>` path or `issue/<n>-<slug>` branch from a prior run makes `git worktree add` hard-fail: read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/contingencies.md § Pre-clean guard` and follow its per-state table first. **Preserve-don't-clobber**: a leftover carrying commits is attached, never cleared (`git branch -D` force-deletes unpushed work silently). A cold run has no leftover.

   The orchestrator owns `git worktree add` and drives each issue **inside** the provided worktree; no dispatched agent cuts its own branch. Use explicit fleet management (`git worktree add -b … / remove / prune`), not generic worktree isolation, which can strand the shared checkout on a stray `issue/<n>` branch and leave worktrees needing prune.

3. **Resolve the concurrency cap, `maxParallelWorkers` (default 4).** Profile key, integer, optional: **absent → 4**; **integer ≥ 1 → that value**; **invalid → 4** (fail-open, no error, `.project/design-philosophy.md#Error & failure philosophy`). `parallel` decides *whether*, `maxParallelWorkers` *how wide*; a sequential run never reaches this step. **"How wide" counts every in-flight leaf agent at once — ONE shared counter spanning Stage A and Stage B** (steps 5, 7 and step 9's recovery ladder), never one window per stage and never concurrent per-issue workers. **Step 6 owns the ladder that hands a freed slot out**; **step 9's recovery fan-out reads the same cap** once every chain has returned. Two run-start decisions are **read, never re-run** here: the DB hazard (*Resolve execution mode*, row 4 — **no** per-Wave DB advisory) and background-dispatch permission (row 2, where the permission pre-flight gate ran).

4. **Run `solve-issue` steps 0 to 2, step 3.5, and the two unnumbered blocks between step 2 and step 3, on the main line, per set issue.** Triage Branch A first — restate the held Phase 0 result inline with ACTUAL VALUES, e.g. `issueStates["<n>"] = { blockers: false, label: null, advisories: [...], risk: "light" }` and `edges["<n>"] = [...]`, the concrete arrays/objects, not the field names; anything absent, label-only, or partial falls to Branch B, the safe default, never an error. Then the root-cause gate and the locked architecture-aware plan, then, in this order:

   | Block | What it resolves |
   |---|---|
   | `solve-issue` `### Build profile resolution` | this issue's `risk` value, which decides the `risk:light` token step 5 puts in the brief and the E2E gate decision. Review effort and the review→fix cycle cap are not resolved here: step 7 classifies both from that issue's built diff |
   | `solve-issue` step 3.5's profile-migration preamble | idempotent; run per issue **inside that issue's worktree**, as that step states it — a no-op on a repo already using `.milestone-config/driver.json` |
   | `### Resolve cited project-docs sections (once, before dispatch)` | the `.project/` sections, the repo file index, and the prose contract |

   **Resolution cadence:** the `.project/` sections and the build profile resolve **per issue**; the repo file index and the prose contract resolve **once per run** (`solve-issue/SKILL.md`'s `### Resolve cited project-docs sections`, sub-steps 5 and 6) and are reused for every issue in every Wave. These blocks stay with the orchestrator: the session that writes the plan briefs the implementer. A step-0 Blocker or a step-2 root-cause miss **parks that issue here** and drops it from the stages below; the rest of the set proceeds.

   **The step-0 Blocker park, under a held `Auto` answer** (`skills/solve-milestone/SKILL.md (the run-start question)`): a Blocker park **still unattempted this run** enters the `## The Auto loop` in `${CLAUDE_PLUGIN_ROOT}/skills/remediate-handoff.md` before that drop — same gated read-direct, on this main line, per set issue, never dispatched, and never copied here. Clean re-triage → park label cleared and the issue **stays in the parallelizable set**, proceeding into step 5's Stage A dispatch on the worktree step 2 already cut for it. A `NEEDS_HUMAN` return or a still-dirty re-triage parks for good (`skills/remediate-handoff.md (Park for good)`); a spent attempt or no `🔴 Triage` comment leaves the park as-is — then the drop above, unchanged. **The step-2 root-cause miss never routes here** — its park comment opens `🔴 Parked — `, not the `🔴 Triage` comment that loop's step 1 reads, so that branch behaves exactly as it does today. No held answer, Leave-them-for-me, or the feeder absent → park immediately, exactly as above.

5. **Stage A: one implementer leaf per set issue, dispatched concurrently.** For each remaining set issue, dispatch the profile's `implementerAgent` as `Agent(run_in_background: true)` per `solve-issue` `### 3. Dispatch the implementer`, briefing it with that issue's approved plan, the profile, the expected file scope, the resolved `.project/` sections / file index / prose contract, `citationFormatPath`, a `risk:light` token when step 4 resolved this issue's build profile to light, and **its worktree path**. Dispatch **concurrently, drawing from step 3's ONE shared in-flight leaf counter** — implementer and reviewer leaves share a single pool of `maxParallelWorkers` slots, so the two stages never sum past the cap. **At Wave start**, dispatch implementers in **ascending issue number** until the counter is full or the set is exhausted; **every later dispatch, implementer or reviewer, is issued by step 6's scheduler** and by nothing else. **If step 4 parked EVERY set issue, this fill dispatches nothing** — no leaf will return and step 6's ladder never runs, so **go straight on the main line to step 9** rather than ending the turn; steps 9 to 11 still owe this Wave its cost record and the fleet cleanup. **The brief MUST also carry this scratch-hygiene rule:** write scratch only under a path named for that issue or that agent, never the shared scratchpad directory, and report what a probe printed rather than writing a probe file to read back later.

   **A dispatched agent is a leaf: it does the work itself, returns an uncommitted diff plus its report, and dispatches nothing** (`docs/architecture.md` → `## Dispatch topology`) — every agent stays at depth 1, where its completion notification reaches the orchestrator. The **per-issue unit gate rides this stage**: each leaf runs `unitTestCmd` in its own worktree as its TDD green step and reports real output; N concurrent unit runs are the hazard the run-start DB interview asks about. The `tests-green` hook re-checks the suite at the orchestrator's own commit (step 8) — a leaf's report is never the only evidence.

   **Leaves never call PushNotification** — the tool is absent from subagent tool registries; the orchestrator holds every park and completion fact and emits at Wave boundaries. **SendMessage addressing:** a dispatched leaf can be sent a mid-run message (delivered at its next tool-use round) **only** by addressing that leaf's own dispatched ID/name — an agent-TYPE name (e.g. `milestone-driver:implementer`) is not a reachable address, and only the session that spawned a leaf can message it.

6. **Gate each implementer return as it lands, and hand its freed slot out — there is NO Stage A barrier.** The moment a leaf returns and clears the gates below, that issue is **review-ready** and step 7 dispatches its reviewer while the rest of the set builds. **Phase 1's one remaining synchronization point is step 9's gather**; the Wave-boundary barrier above is the Wave's other one, untouched. **End the turn while waiting** — never poll with no-op tool calls or a tight loop; the harness re-invokes the orchestrator as each leaf completes. A long-interval background `until`-loop (several minutes, not seconds) is acceptable only as a safety net against a hung leaf that never returns a completion notification, never as the primary wait mechanism.

   **The shared-slot scheduler — the ONLY place a leaf is dispatched after step 5's initial fill.** `maxParallelWorkers` (step 3) bounds **one** counter over **all** in-flight leaves: implementer, coherence, and reviewer alike. **Every leaf return frees exactly one slot, and every freed slot is filled by exactly one dispatch** — with a single carve-out, the **coherence leaf**, whose return does **not** free a slot but **hands it straight to that issue's reviewer** (step 7 pairs the two), so an issue in Stage B occupies **exactly one slot** whether or not `coherenceReviewAgent` is configured. Run this ladder on each freed slot, **top-down, first match wins**:

   | # | Condition | Dispatch |
   |---|---|---|
   | 1 | **An already-started chain owes a re-dispatch** — this step's unit-retry re-dispatch, or step 7's review→fix re-dispatch | Dispatch it. If the counter is full when one comes due, it waits for the next freed slot and takes it **ahead of rows 2 and 3** |
   | 2 | **A review-ready issue is waiting** | Enter step 7 for the **oldest** one — its coherence leaf when step 7's gate actually runs one, its reviewer leaf otherwise. **Selecting an issue DEQUEUES it immediately**, before any further ladder pass, so two frees in one batch pick two *different* issues. **"Oldest" is by the order implementer leaves RETURNED** — **not** issue number, **not** dispatch order. Ties (two returns in one notification batch) break by **ascending issue number** |
   | 3 | **No review-ready issue is waiting, and a set issue has not been dispatched yet** | Dispatch the next **implementer** leaf, in **ascending issue number**, briefed exactly as step 5 briefs one |
   | 4 | **Nothing to dispatch** | **First run every per-issue tail (step 8) still owed** — each issue whose review converged this turn and has not been tailed; an untailed issue reaches step 9 with no commit, no PR and no park label, precisely the `abandoned` shape. **A tail's gates run on the main line and hold no slot, but a RED gate re-dispatches that issue's implementer leaf into its worktree (step 8's at-most-2 cap) and that leaf DOES take one** — read the counter *after* the tails, never before. **Then:** any leaf still in flight → **end the turn** and wait for the next completion notification; no leaf in flight either → **do NOT end the turn**, continue on the main line to step 9's gather. Only a leaf completion re-invokes the orchestrator, so ending the turn on an empty counter strands the Wave with steps 9 to 11 unrun |

   **A park frees NO extra slot** — every park below fires *after* that issue's leaf returned and already freed its one slot. A park **removes that issue from the review-ready queue and from row 3's candidates**; the ladder skips it on the free its own leaf produced. Step 4's triage park is earlier still: that issue never becomes a candidate. A park is never a wait, and one issue's park never delays another's dispatch.

   **On each completion notification, verify that leaf's report and apply `solve-issue` step 3's gates.** First check the report honors the implementer contract (least-code / reuse-first, TDD red→green observed or a `VERIFICATION (no test layer)` section, verified citations, a Decision Log, a `USER-FACING CHANGES` block, changes left uncommitted). Then apply that step's four gates:

   | Report signal | Condition | Park label |
   |---|---|---|
   | `NEW_UI_ELEMENTS: yes` | acceptance criteria silent on the element's visual/UX detail | `needs design` |
   | `DESTRUCTIVE_OPS: yes` | the confirm flow unspecified | `needs decision` |
   | a reported new dependency | — | `needs decision` |
   | implementer `STATUS: STOPPED` | — | that gate's own label rule (`needs design`, `needs decision`, or `blocked`) |

   Each park posts its `🔴 Parked — ` comment, applies its label (plus `in progress` when the branch has commits), preserves the branch, and **drops the issue from Stage B and from the per-issue tail**. A park that returned a diff is still a park: it does not reach review, commit, push, or PR.

   **A fifth branch, and it is not a park:** an implementer `STATUS: COMPLETE` with an **empty** `FILES CHANGED` list and a clean worktree is a **no-change outcome** — this issue's acceptance criteria are already satisfied by `<base>`. It is reachable by contract (`agents/implementer.md`'s STATUS enum is `COMPLETE | STOPPED | PAUSED-FOR-APPROVAL`, and its `## Output format` never requires a non-empty `FILES CHANGED`). Record it, apply **no** park label, and drop the issue from Stage B, the per-issue tail, and step 9's partition. **Decide it here, at the step that reads the report, never at step 9** — step 9 reads artifacts alone, and a clean zero-commit worktree is byte-identical whether the leaf finished correctly or died before writing anything.

   **A red unit suite in a leaf's report** → the orchestrator owns the retry loop; read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/contingencies.md § Red unit suite retry loop` (at most 2 re-dispatches, then park **`blocked`**). The leaf cannot loop on a red result itself. Every leaf returning green skips it.

7. **Stage B: review, concurrently, from the orchestrator — entered per issue, as each becomes review-ready.** For each issue whose implementer **returned a diff and cleared step 3's gates** (step 6), run `solve-issue` step 6.1's review-and-resolve procedure against that worktree's **uncommitted** changes, **in the dispatch shape pinned below and in no other**, **one issue at a time, from step 6's scheduler, never as a set**. **Run `solve-issue` section 6's unnumbered coherence-review block first**: the `coherenceReviewAgent` pass, never-gating, dispatched read-only against that worktree's uncommitted diff **as `Agent(run_in_background: true)`, like every other leaf** — so it is counted. **It and the reviewer share this issue's ONE Stage B slot** (step 6's carve-out): the coherence leaf takes the slot when row 2 picks the issue, and **on its return the orchestrator dispatches that issue's reviewer into the same slot directly, without re-entering the ladder**. **The gate is `solve-issue`'s own: present AND configured**, skipping silently when either leg fails — and its default-fill leaves **configured true but present false on a fresh install**, so skipping is the ordinary case. **Whenever it skips, no coherence leaf is dispatched and none will ever return, so the slot passes STRAIGHT to the reviewer in the same turn.** Never commit a slot to a leaf that was not dispatched.

   **Resolve this issue's review depth first, on the orchestrator's main line**, never inside the reviewer leaf and never inside any other agent. Immediately before dispatching that issue's reviewer, run `${CLAUDE_PLUGIN_ROOT}/scripts/classify-review-depth.<sh|ps1> <worktree-path>` (pwsh on Windows, bash elsewhere) and take its printed verdict verbatim, never re-derived and never overridden (`skills/solve-issue/post-fix-commit.md (The verdict is the script's, never the agent's)`): `deep` sets `medium` effort and 2 cycles; `standard` sets `medium` and 1 cycle, a 2nd only on a Critical or Important finding; `shallow` sets `low` and 1 cycle, a 2nd impossible. The script reads `git diff HEAD` inside that worktree, which at review time is still `<base>`, because Phase 1 does not commit until step 8. An unresolvable worktree root, absent git, or an empty candidate set fails open to the script's own `standard` on stdout at exit 0, never a crash and never a park (`.project/design-philosophy.md#Error & failure philosophy`). A review→fix re-dispatch re-runs it against the new diff before the 2nd cycle, and the cap stays whatever the **first** verdict set: a verdict dropping to `shallow` ends the loop, one rising to `deep` grants no 3rd cycle. **A second cycle returning any Critical or Important finding parks the issue `needs design`, with the park comment stating that a second review round returned a Critical or Important finding. No third cycle runs.**

   **The dispatch shape, pinned: exactly one reviewer leaf per issue, and nothing nested.** Dispatch **one** review subagent per issue as `Agent(run_in_background: true)`, occupying one slot of step 3's **shared** counter, the single-reviewer dispatch `superpowers:requesting-code-review` defines: one `general-purpose` subagent filled from its `code-reviewer.md` template. Brief each with the issue's description and acceptance criteria (the template's `DESCRIPTION` and `PLAN_OR_REQUIREMENTS`), the profile (`sourceGlobs`, `nonNegotiables`), the review effort the verdict just computed for that issue's worktree diff sets, that issue's worktree path, `citationFormatPath`, and the changes to review. **Name the changes as the worktree path plus `<base>`, not as a `BASE_SHA..HEAD_SHA` range:** Stage B reviews uncommitted work, which that range does not address, so the reviewer diffs the working tree against `<base>` in the worktree it was given. Each reviewer returns findings only, in the template's shape (Strengths, then Critical / Important / Minor issues each naming a ref per `citationFormatPath`, then its assessment), which the orchestrator folds into that issue's `## Code Review` section (`skills/output-style.md`). A reviewer edits nothing, commits nothing, and dispatches nothing. **The brief MUST also carry the same scratch-hygiene rule as the Stage A brief above.**

   **The brief MUST also put comment text out of review scope:** no finding at any severity about a comment's wording, density, or presence. One carve-out, in these terms and not redefined: a comment change altering a machine-read directive stays in scope, `scripts/classify-delta.sh (is_directive <src>)`'s enumeration deciding what counts as one.

   **The orchestrator never dispatches an agent that itself runs `/code-review`.** That command fans out internally, seating every one of its reviewers at depth 2, where a completion notification never arrives and the pipeline stops mid-cycle with the work uncommitted (`docs/architecture.md` → `## Dispatch topology`).

   **The gate is unchanged and unconditional:** an omitted review is a park trigger (`solve-issue` step 6.1, its `/code-review` gate row, and its Autonomy model), and `hooks/code-review-gate.sh` still denies a PR whose body carries no `## Code Review` section. An in-scope finding re-dispatches that issue's implementer leaf under step 6.1's own verdict-keyed review→fix cap (the fresh review the last action before commit on a `code-changed` delta); a park-trigger finding parks that issue and drops it from the rest of Phase 1.

8. **Per-issue tail, orchestrator-run: remaining parallel-safe gates, then version bump, commit, push, PR.** **No barrier here either:** the tail runs per issue **as that issue's review converges** (step 7), so an issue that clears review first ships first; with step 6's Stage A barrier removed, **steps 5 to 8 are one unbroken per-issue chain**. **Do not re-run** the unit gate (step 5, with step 6's retry loop) or the review with its resolve loop (step 7). **Run now, per issue, in its worktree:** the **static** `preflightCmd` only, the lint / format / static-analysis / security-scan class. **Deferred to the serial tail** (Phase 2 step 2's re-verify): **E2E**, any **server-starting** preflight, and a UI issue's **render capture**, all of which bind the same fixed port, so they run once there against accumulated integrated state rather than contending across worktrees. **Escape hatch:** a consumer injecting a per-worktree `PORT` keeps such a gate (capture included) in this phase. Each gate keeps its own cap (at most 2 for preflight; the review's own verdict-keyed cap for any re-review it triggers), applied where the gate runs.

   Then run `solve-issue` steps 6.2 to 6.6 in that worktree as that file states them, so the Decision Log, the **Code Review** section, the version bump, the commit, and the push / PR-open inherit their `integrationGranularity` conditionals (`### Integration granularity` below). Every issue applies the same idempotent same-line bump to the shared `plugin.json` target, which the tail's 3-way merge reconciles without conflict. **Nothing merges here:** Phase 1 builds and does not integrate.

9. **Derive terminal state from git/gh, never from an agent's self-report — ONCE per Wave, as a gather.** **This step is Phase 1's one barrier, holding the guarantee the removed Stage A barrier used to give:** run it **once**, after **every** dispatched chain for the Wave has returned — every implementer leaf and its re-dispatches, every reviewer leaf, every per-issue tail (step 8) — and **never per issue as a chain finishes**. Await those completions the way step 6 describes, ending the turn while waiting. The `abandoned` legs below key on the **absence** of artifacts, which a mid-build issue presents identically: probing a live leaf would classify a healthy in-flight issue `abandoned` and dispatch a **second** implementer into the worktree the first is still writing. Then, per dispatched issue, **derive terminal state from git + gh ground truth**:

   **Wave-state checkpoint — consult before probing (resume optimization).** Before probing a dispatched issue, check `.milestone-config/.runtime/wave-state.json` for that issue's entry — a persisted cache of this step's own output from a prior pass. It decides only whether the probe runs for that issue this pass:
   - **Read, degrade-to-empty on absent/corrupt.** `jq . .milestone-config/.runtime/wave-state.json 2>/dev/null` (Bash) / the try/`ConvertFrom-Json` pattern (PowerShell) — absent, unreadable, or invalid JSON is treated identically to "no entry for any issue": fall straight through to the probe below for every issue in the set. Mirrors `triage-cache.json`'s degrade-to-empty read (`scripts/triage-cache.sh (lookup: degrade to an empty cache)`); fail-open, never a crash (`.project/design-philosophy.md#Error & failure philosophy`).
   - **An entry exists for this issue** → read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/contingencies.md § Wave-state checkpoint freshness` and apply it. A **fresh `built-green`** entry is trusted directly, in place of the probe; **every other outcome** — stale, or any `parked` or `abandoned` entry at any freshness — falls through to the probe below. **No entry for this issue** → the probe below, reading nothing.

   For every issue that falls through (no fresh checkpoint hit):
   - run the `solve-issue` **step-3 branch-state probe** against that issue's worktree branch — PR state for `issue/<n>-*` (path-a query `gh pr list --state all --limit 200 --json number,headRefName,state,url --jq '.[] | select(.headRefName | startswith("issue/<n>-"))'`), commits ahead of `<base>` (path b, `git rev-list --count <base>..issue/<n>-<slug>`), and park state from **live labels** (`gh issue view <n> --json labels` — `needs design` / `needs decision` / `blocked`) plus the `🔴 Parked` / `🔴 Triage` / `🔴 Blocked` comment (the signal the sequential loop reads at step 4);
   - derive `isUI` independently from `git diff <base>...HEAD --name-only` ∩ `uiSurfaceGlobs`, never from a PR's changed-file list.

   **Partition the dispatched set into `built-green`, `parked`, and `abandoned` from the ground-truth derivation, not from parsing any final message. Those three are exhaustive and mutually exclusive; the first two alone are not exhaustive:**

   | Bucket | Ground truth | Handling |
   |---|---|---|
   | **`built-green`** | An open PR for `issue/<n>-*` (path a), **or** a **pushed** branch carrying commits ahead of `<base>`, **and** no park label. **Pushed-ness needs its own read:** path b counts *local* commits, so confirm the push with `git ls-remote --heads origin issue/<n>-<slug>` (non-empty) and never infer it from a non-zero path-b count alone | The green set Phase 2 receives. An unpushed branch read as `built-green` reaches Phase 2, whose step 2 runs `gh pr merge --squash --delete-branch` against a PR that does not exist |
   | **`parked`** | the probe found a park label (`needs design` / `needs decision` / `blocked`) with its `🔴 Parked` / `🔴 Triage` / `🔴 Blocked` comment | **Excluded from the merge tail**, with **branch, label, and comment intact**. Do not re-park or re-label — omit the issue from Phase 2, as the sequential loop does. **Emit one `⏸️ #N parked — <reason>` notification** (reason = the live label plus that comment's reason) **before emitting the aggregate 🌊 wave-boundary notification** |
   | **`abandoned`** | **Neither bucket above:** **no PR** (path a), **no pushed branch carrying commits ahead of `<base>`** (`git ls-remote --heads origin issue/<n>-<slug>` empty, or non-empty with a 0 path-b count), and **no park label** | The recover-once ladder below. **Do not park it on sight** — nothing is known to be wrong, and `skills/solve-milestone/SKILL.md (no blocker label)`'s buildability condition (b) would block the rebuild until a human clears the label |

   **`abandoned` is a named third bucket, never a fall-through** — an auto-denied background leaf (`skills/solve-issue/SKILL.md (Background subagents auto-deny any)`), context exhaustion, and a killed run all land here; without the bucket they vanish with no label, comment, or notification.

   **A non-empty `abandoned` bucket** → read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/abandoned-recovery.md` and run its recover-once ladder (cap 1) **inside this same pass**, so every dispatched issue leaves step 9 as `built-green` or `parked`. An **empty** bucket never reads that file and goes straight to the checkpoint write below.

   **Wave-state checkpoint — write after deriving.** Immediately after this step's terminal state is established for a dispatched issue — freshly derived, or trusted from a fresh checkpoint entry — write/update that issue's entry in `.milestone-config/.runtime/wave-state.json`. Per issue, immediately, not batched to Wave end (mirrors `triage-cache.json`'s read-modify-write discipline, `skills/triage/SKILL.md` Step 6.5):

   ```json
   {
     "<issue_number>": {
       "issue": <n>,
       "wave": <N>,
       "status": "built-green" | "parked" | "abandoned",
       "branch": "issue/<n>-<slug>",
       "pr": "<PR URL>" | null,
       "isUI": true | false,
       "derivedAt": "<ISO 8601 UTC timestamp of this derivation, e.g. via `date -u +%Y-%m-%dT%H:%M:%SZ`>"
     }
   }
   ```

   - **`branch` is always required** — the freshness anchor for the no-per-issue-PR cases, and the one field the probe cannot re-glob for after the fact.
   - **`pr`** is the PR URL when a per-issue PR exists; `null` for a `parked` or `abandoned` entry.
   - **`"abandoned"` is a defensive enum value this step never writes.** The recover-once ladder resolves every `abandoned` classification to `built-green` or `parked` before this write fires. It is in the enum, and in the never-trust scope above, so an entry written by hand or by a future path never shortcuts. A run killed mid-recovery needs no entry: a missing one already falls through to the full probe.
   - **Write mechanics mirror `triage-cache.json` verbatim** (`skills/triage/SKILL.md` Step 6.5): `mkdir -p .milestone-config/.runtime` first (no writer may assume the directory exists), then merge this issue's entry into the existing object keyed by issue number — `jq --arg n "<n>" --argjson entry '<entry-json>' '.[$n] = $entry'` read via a temp file and `mv`'d into place (Bash), or `ConvertTo-Json -Depth 10` + `Set-Content -Encoding utf8NoBOM` (PowerShell) — no external-tool dependency on that path.
   - **Best-effort, fail-open.** A write failure (permissions, disk, concurrent-run collision) logs one line and continues the run; the file is a resumability optimization, never the source of truth (`.project/design-philosophy.md#Error & failure philosophy`).
   - **No new gitignore entry needed.** `.milestone-config/.runtime/` is already listed in the committed `.milestone-config/.gitignore` and in `.project/environment.md#Data stores`; `wave-state.json` inherits the ignore as-is.

10. **Cleanup the fleet.** Remove a worktree once it is integrated by Phase 2, **or** its issue parked (**except** an issue parked by step 9's recover-once ladder, whose worktree is preserved until Wave end / run end so the recovery evidence that park's comment cites survives for a human to read), **or** at Wave end / run end:

    ```
    git worktree remove .milestone-config/worktrees/issue-<n>
    ```

    A built-green issue's branch was already **pushed** at step 8 and has a PR open, so its **local worktree is safe to remove at Wave end / run end regardless of Phase 2** — which prevents built-green worktrees from being orphaned and, with step 2's pre-clean guard, keeps the next parallel run collision-free. Run `git worktree prune` **best-effort** at Wave end, at run end, and on systemic failure. The scratch dir `.milestone-config/worktrees/` is gitignored, so the fleet never pollutes the working tree or a commit. (A leftover old-named `.milestone-driver-worktrees/` dir in an existing clone is harmless: gitignored and unused.)

11. **Hand the green set to Phase 2, and emit one cost record per Wave.** The per-issue tail never returns to a caller, so `solve-issue`'s `## Run-end cost record` never fires per issue: **Phase 1 emits one record per Wave** — aggregate every dispatch this Wave made (implementer leaves with their re-dispatches, reviewer leaves, any coherence pass) into one record keyed by the Wave, following that section's aggregate / map / emit steps unchanged. Additive, never-gating. The `built-green` set is held (branches built + pushed) for **Phase 2 — the serial verified merge tail**. Phase 1 performs **no merge to `integrationBranch`**.

**Blast-radius boundary unchanged.** As in sequential mode, Phase 1 and the serial tail merge only to `integrationBranch`, **never** `protectedBranch`.

### Parallel mode — Phase 2: serial verified merge tail

Applies **only** when the run resolved to **parallel** mode (see the *Resolve execution mode* Before-starting step). Runs **after** Phase 1, consuming the `built-green` set Phase 1 derived, and **to completion at the end of each Wave, before the next Wave's Phase 1 step 1 cuts its worktree fleet from the same target**. **Parked** issues are excluded — Phase 1 already omitted them, branch + label + comment intact. **The tail integrates every built-green branch, UI included.** Under a non-default `integrationGranularity`, apply `integration-granularity.md`'s **`## Phase 2 deltas`** table to every step below.

**Run on the main working tree** (not in a worktree), over the built-green branches in **ascending-issue order**. **Force-free by default (merge-in — no history rewrite).** The **integration target advances after each merge**, so two same-Wave siblings touching overlapping files are re-verified against each other — the "every increment tested against accumulated state" guarantee naive concurrent merging throws away. For each such branch:

1. **Merge the integration target INTO the issue branch.** `git fetch`, then `git merge <target>`, where `<target>` is `integrationBranch`. This brings accumulated state onto the issue branch as an ordinary merge commit — a **fast-forwardable** push, **no `--force`**.
2. **Clean merge** → push (fast-forward) → **re-verify against accumulated state**: run `unitTestCmd` if defined, **plus the E2E / port-binding gates Phase 1 deferred** (its step 8), **once here against accumulated integrated state**. On green → `gh pr merge --squash --delete-branch` → re-sync local `integrationBranch` (`git fetch`, fast-forward); the `--squash` collapses the merge-in commit so the target's history stays linear. **A UI issue's render capture runs here under the default `"issue"` granularity**, among those deferred fixed-port gates and **before** the squash-merge so its comment lands on a live PR: with a complete `visualCapture` block, read `${CLAUDE_PLUGIN_ROOT}/skills/solve-issue/visual-capture.md` and follow its `### Capture flow`, whose Publish step posts the shots as a PR comment. **Evidence, never a gate** — an absent or incomplete block, a capture failure, or a `suspected-issue` pre-filter verdict logs one line and the merge proceeds unchanged (`.project/design-philosophy.md#Error & failure philosophy`).
3. **Conflict** → **bounded auto-resolve**: read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/contingencies.md § Merge-conflict bounded auto-resolve` and follow it. **Resolvable AND green** → proceed to step 2's merge. **Non-trivial / ambiguous OR red** → `git merge --abort`, **park `blocked`** (comment + label + preserve branch), continue with the next branch.
4. **Clean merge but red re-verify** → **park `blocked`** (the combination is broken; a human decides), continue with the next branch.

**Why merge-in, not rebase + force (field-found).** A history-rewriting push is fragile across consumer safety setups: in a real run `--force-with-lease` (and the delete-then-fresh-push fallback) were **BLOCKED** by two independent guards — a consumer destructive-command hook treating the safe `--force-with-lease` like a raw `--force`, and the runtime's destructive-action classifier. A `no-push` hook permitting the push is **necessary but not sufficient** when those guards stand. **Merge-in gives the identical re-verify guarantee with no history rewrite**, so it is the default. The **rebase + `--force-with-lease` variant stays available** as the alternative, but it **MUST be allow-listed** in the consumer's hooks / destructive-action classifier first.

**Wave-boundary notification.** After Phase 2 completes for a Wave (all built-green branches merged, UI included, parked issues excluded) and before the next Wave's Phase 1 begins, emit a `PushNotification` — **only when another Wave follows** (🌊 is suppressed on the final Wave; the 🏁 run-complete notification is the single end signal):
```
🌊 Wave N done · X/Y ✅ · next: Wave N+1
```
Where N = the just-completed Wave number, X = issues merged this Wave (built-green, by Phase 2), Y = total issues in this Wave (all outcomes: merged + parked + triage-parked), next = Wave N+1 number. Parked-wave notifications (Class 1, per-issue) are emitted individually as each park occurs; this one covers the Wave's aggregate result.

### Integration granularity (issue vs wave)

`integrationGranularity: "issue" | "wave" | "milestone"`, default `"issue"` (`docs/profile-schema.md (How should built issues integrate?)`). It controls **how built issues integrate**, and is **orthogonal to the parallel/sequential execution mode** (which controls *how* issues build). Any of {sequential, parallel} × {`"issue"`, `"wave"`, `"milestone"`} is valid.

**`"issue"` (default).** Each built issue opens **its own PR** → its own CI run → merges individually: in sequential mode each issue's `solve-issue` opens and merges its own PR; in parallel mode the Phase 2 serial verified merge tail merges each built-green PR in turn. Every step of Phase 1 and Phase 2 above is written for this value.

**`"wave"` and `"milestone"` — the branch point.** When the profile resolved either value at run start, read `${CLAUDE_PLUGIN_ROOT}/skills/solve-milestone/integration-granularity.md`: it holds both values' own mechanics (wave branch, one wave PR, explicit issue close; and the milestone-branch pointer into `milestone-granularity.md`) **plus** the per-step deltas they apply to Phase 1 and Phase 2 above, as two tables keyed by site. Under the `"issue"` default that file is **never read**. Missing or unreadable once granularity has resolved to `"wave"` or `"milestone"` is a **systemic failure**, the same class as a missing `parallel-waves.md`; do **not** silently degrade to `"issue"`.
