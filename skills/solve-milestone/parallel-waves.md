# Parallel waves — solve-milestone reference

This file is loaded by solve-milestone when the run resolves to parallel mode (the *Resolve execution mode* Before-starting step, per the mode branch point at the top of `### 4. Loop over issues in dependency-graph order` in core `SKILL.md`). It holds the Wave loop's parallelizable-set selection, the two-phase concurrent-build-then-serial-merge-tail machinery, and the issue/wave integration-granularity mechanics. If this file is **missing or unreadable** at the point core `SKILL.md` needs it (mode already resolved to parallel), that is a **systemic failure** — surface it and halt the run per core `SKILL.md`'s `## Autonomy` → "Systemic failures that halt the run" (the same class as missing required tooling); do **not** silently degrade to sequential (which would silently skip real dispatched work), and do not fail with an uninformative crash.

**Contents.** Selecting the concurrent set · Phase 1: pipelined build and review · Phase 2: the serial merge tail · Integration-granularity values.

---

### Parallelizable-set selection (parallel mode)

**The parallelizable set.** From the issues in the current Wave, an issue belongs to the parallelizable set **iff both** hold:

- it is **buildable this pass** — the three conditions **(a)/(b)/(c)** already defined above (every issue in `dependencyGraph.edges["<n>"]` merged to `integrationBranch`, or, under `integrationGranularity: "milestone"`, carrying its `Issue: #<n>` trailer on the milestone branch, since nothing merges to `integrationBranch` before milestone end (`milestone-granularity.md § Resume and buildability from the trailer`); no live blocker label; `issueStates[n].blockers == false`); **AND**
- it carries **no `dependencyGraph.edges["<n>"]` edge to another issue currently in the same candidate set** (mutual independence).

In short: the set is **buildable ∧ mutually-independent**. (Do not re-derive buildability here — it is exactly the (a)/(b)/(c) definition the sequential loop already uses; this subsection only adds the intra-set independence guard.)

**Why the intra-set edge check is a guard, not the workhorse.** Its real job is the **shared-file-but-not-a-build-dependency** case: two same-Wave issues whose files overlap are **not** a build-time dependency (their files are disjoint *at build*), so triage draws **no `DEPENDS_ON` edge** between them and they correctly stay in the set. That overlap surfaces only **at merge**, where the orchestrator-owned **serial verified merge tail** (#73) reconciles it (git's `ort` strategy auto-resolves **non-adjacent** edits to the same file; two edits on directly adjacent lines conflict). Field-validated: two issues each appended a distinct child route to the same `app.routes.ts` — no `DEPENDS_ON` edge, both built concurrently, and the two additions auto-merged in the serial tail.

### Parallel mode — Phase 1: concurrent stage dispatch

Parallel mode splits into two phases that share this skill's Phase 0 triage and dependency graph:

- **Phase 1 (this issue, #72)** — **pipelined build and review**: each issue's reviewer is dispatched the moment that issue's implementer returns and clears step 6's gates, **not** after the slowest implementer in the Wave returns (#400). Builds the parallelizable set in a worktree fleet, but **does not integrate**. The green set is assembled at step 9's wave-level gather and held (branches built + pushed; built only, nothing pushed, under `integrationGranularity: "milestone"`) for Phase 2. **Concurrency is by stage, not by issue:** the orchestrator fans out one leaf per issue per stage and is itself the only session that fans out (`docs/architecture.md` → `## Dispatch topology`).
- **Phase 2 (#73)** — the **serial verified merge tail**. Integrates the held green set to `integrationBranch` (the milestone branch under `integrationGranularity: "milestone"`) one branch at a time, running the deferred gates (E2E, any server-starting preflight) once against accumulated state. See `### Parallel mode — Phase 2: serial verified merge tail` below.

When active, after Phase 0 triage, process the milestone **Wave by Wave** (same Wave order the sequential loop uses). **Each Wave runs to completion across BOTH phases before the next Wave begins:** Phase 2 runs to completion at the end of the Wave — its squash-merges land on `integrationBranch` (the milestone branch under `integrationGranularity: "milestone"`) and the local `integrationBranch` is re-synced (a no-op under milestone granularity, where nothing was pushed) — **before** the next Wave's Phase 1 step 1 cuts its worktree fleet from that same target. Call this the **Wave-boundary barrier**. **A Wave has exactly TWO barriers and #400 relaxes neither:** this one, and **step 9's gather**, Phase 1's own, which sits before it. Pipelining removes only the Stage A → Stage B boundary *inside* Phase 1. Phase 2 stays serial: cross-issue reconciliation happens there and needs every branch present, which is exactly the set step 9's gather assembles. For each Wave:

1. **Compute the parallelizable set.** Per the `### Parallelizable-set selection` subsection above: the set is **buildable ∧ mutually-independent** (the (a)/(b)/(c) buildability conditions plus the intra-set independence guard). An empty set (every Wave issue parked or dependency-held) advances to the next Wave with nothing dispatched.

2. **Create the worktree fleet (orchestrator-owned).** The orchestrator creates **one worktree per set issue** into the gitignored scratch dir `.milestone-config/worktrees/`, cut from `<base>`. **`<base>` is `integrationBranch`, or the milestone branch `milestone-<number>-<slug>` under `integrationGranularity: "milestone"`** (`milestone-granularity.md § Branch model`), and it names that branch everywhere below (steps 2 and 5), the same way `<target>` parameterizes the Phase 2 tail:

   ```
   git worktree add .milestone-config/worktrees/issue-<n> -b issue/<n>-<slug> <base>
   ```

   **Pre-clean guard (resume-aware: makes fleet creation idempotent / re-runnable without destroying in-progress work).** `git worktree add` hard-fails if either the path `.milestone-config/worktrees/issue-<n>` or the branch `issue/<n>-<slug>` is a leftover from a prior or interrupted run (`fatal: '…' already exists`, or `fatal: a branch named '…' already exists`), and `git worktree prune` does **not** remove an intact leftover directory. But a leftover branch may carry **real in-progress work** — commits from a prior run that was interrupted (or parked) after committing but before pushing. `git branch -D` is a **force** delete that silently discards such unpushed commits, so the guard must **preserve-don't-clobber**: clear only provably-safe leftovers, and **resume** any leftover that carries work. Before each `git worktree add`, decide per leftover branch `issue/<n>-<slug>`:
   - **No leftover at all (cold case):** `git worktree add .milestone-config/worktrees/issue-<n> -b issue/<n>-<slug> <base>` as shown above.
   - **Leftover branch carries commits ahead of `<base>` that are not yet pushed/merged** (in-progress work from an interrupted or parked prior run — check with `git rev-list --count <base>..issue/<n>-<slug>` and confirm those commits are not on `origin/issue/<n>-<slug>`; under `integrationGranularity: "milestone"` `<base>` is the milestone branch, the `origin` confirmation drops as unsatisfiable because nothing is pushed, and "not yet merged" reads as "no `Issue: #<n>` trailer on that branch"): do **NOT** `git branch -D`. **Attach a worktree to the existing branch** — `git worktree add .milestone-config/worktrees/issue-<n> issue/<n>-<slug>` (no `-b`; checks out the existing branch with its commits) — and drive that issue against it. The `solve-issue` branch-state probe (resume paths (a)/(b)/(c)), which the orchestrator runs on the main line, then **resumes** that work instead of losing it. (If a stale worktree **directory** is registered at that path, `git worktree remove --force .milestone-config/worktrees/issue-<n>` / `git worktree prune` the directory entry first — but the **branch and its commits are preserved**.)
   - **Leftover is provably safe to discard** — the branch is **0 commits ahead** of `<base>`, **or** already merged, **or** already pushed (its work survives on `origin`); under `integrationGranularity: "milestone"` "already pushed" is **not** a discard-safe condition at all (no issue branch is ever pushed) and "already merged" resolves to already squash-merged onto the milestone branch, evidenced by its `Issue: #<n>` trailer (`milestone-granularity.md § Resume and buildability from the trailer`): clear it fully — `git worktree remove --force .milestone-config/worktrees/issue-<n>` (if registered/present), `git worktree prune` (clear stale admin entries), `git branch -D issue/<n>-<slug>` — **then** create fresh with `git worktree add .milestone-config/worktrees/issue-<n> -b issue/<n>-<slug> <base>`.

   This **mirrors** the plugin's resume culture (`solve-issue`'s branch-state probe / resume paths (a)/(b)/(c)): re-running preserves in-progress work and only clears leftovers that are provably safe to discard — never force-deleting a branch that carries unpushed commits. **Under `integrationGranularity: "milestone"` the marker is integrated-or-not, not pushed-or-not:** every issue branch there is unpushed, so pushed-or-not separates nothing, and the branch that is safe to discard is the one whose `Issue: #<n>` trailer is already on the milestone branch.

   The orchestrator owns `git worktree add` — it drives each issue **inside** the provided worktree, and no dispatched agent ever cuts its own branch. Use explicit fleet management (`git worktree add -b … / remove / prune`); do **not** lean on generic worktree isolation, which can strand the shared checkout on a stray `issue/<n>` branch and leave worktrees needing prune.

3. **Resolve the concurrency cap, `maxParallelWorkers` (default 4).** Read the `maxParallelWorkers` profile key (integer, optional): **absent → 4** (today's default, unchanged); **integer ≥ 1 → that value**; **invalid (non-integer OR `< 1`) → 4** (fail-open, no error, per `.project/design-philosophy.md#Error & failure philosophy`). The cap is **orthogonal to the resolved parallel/sequential mode** — `parallel` decides *whether* to parallelize, `maxParallelWorkers` decides *how wide*; it has **no effect on a sequential run** (which never reaches this step). **"How wide" counts every in-flight leaf agent at once — ONE shared counter spanning Stage A and Stage B** (steps 5, 7 and step 9's recovery ladder), never one window per stage and never concurrent per-issue workers; the key name, its default, and its fail-open resolution are unchanged. **Step 6 owns the ladder that hands a freed slot out** while Phase 1's chains are live; **step 9's recovery fan-out reads the same cap** once they have all returned. The default 4 is a safe, conservative value (field-validated: 5 concurrent builds + 5 reviews ran with no contention); a repo that knows its setup (no shared DB, ample cores, generous rate limits) can raise or lower it. The DB-hazard decision was already made once at run start (the *Resolve execution mode* Before-starting step, row 4) — there is **no** per-Wave DB advisory here. The background-dispatch permission decision was likewise **resolved once at run start** (row 2 — the permission pre-flight gate ran there); this step **reads** it and does not re-run the gate. If that resolution found a gap, the run already resolved to sequential/synchronous and this path is not reached.

4. **Run `solve-issue` steps 0 to 2, step 3.5, and the two unnumbered blocks between step 2 and step 3, on the main line, per set issue.** Triage Branch A (reusing the held Phase 0 result as an explicit inline restatement with ACTUAL VALUES — e.g. `issueStates["<n>"] = { blockers: false, label: null, advisories: [...], risk: "light" }` and `edges["<n>"] = [...]`, the concrete arrays/objects, not just the field names; anything absent, label-only, or partial falls to Branch B, the safe default, never an error), then the root-cause gate and the locked architecture-aware plan. Then, in order: `solve-issue` `### Build profile resolution` (it resolves this issue's `risk` value, which decides the `risk:light` token step 5 puts in the brief and the review effort step 7 dispatches at), `solve-issue` step 3.5's idempotent profile-migration preamble (run per issue inside that issue's worktree, exactly as that step states it; a repo already on `.milestone-config/driver.json` is a no-op there), and `### Resolve cited project-docs sections (once, before dispatch)`. **Resolution cadence, because these blocks differ:** the `.project/` sections and the build profile resolve **per issue**; the repo file index and the prose contract resolve **once per run** (`solve-issue/SKILL.md`'s `### Resolve cited project-docs sections`, sub-steps 5 and 6, both say so) and are reused for every issue in every Wave, never re-resolved. Naming these blocks is what keeps a heavy issue from being reviewed at whatever effort the reader picks and a light issue from silently losing its verification mode. These stay with the orchestrator because the session that writes the plan is the session that must brief the implementer. A step-0 Blocker or a step-2 root-cause miss **parks that issue here** and drops it from the stages below; the rest of the set proceeds.

5. **Stage A: one implementer leaf per set issue, dispatched concurrently.** For each remaining set issue, dispatch the profile's `implementerAgent` as `Agent(run_in_background: true)` per `solve-issue` `### 3. Dispatch the implementer`, briefing it with that issue's approved plan, the profile, the expected file scope, the resolved `.project/` sections / file index / prose contract, a `risk:light` token when step 4 resolved this issue's build profile to light, and **its worktree path**. Run the dispatches **concurrently, drawing from step 3's ONE shared in-flight leaf counter** — implementer and reviewer leaves share a single pool of `maxParallelWorkers` slots, so the two stages can never sum past the cap. **At Wave start**, dispatch implementers in **ascending issue number** until the counter is full or the set is exhausted; **every later dispatch, implementer or reviewer, is issued by step 6's scheduler** and by nothing else. **If step 4 parked EVERY set issue, this fill dispatches nothing** — no leaf will ever return, so step 6's ladder will never run and **go straight on the main line to step 9** (whose gather has nothing to await) rather than ending the turn — steps 9 to 11 still owe this Wave its cost record and the fleet cleanup for the worktrees step 2 created. **The brief MUST also carry this scratch-hygiene rule:** write scratch only under a path named for that issue or that agent, never the shared scratchpad directory, and report what a probe printed rather than writing a probe file to read back later.

   **A dispatched agent is a leaf: it does the work itself and returns an uncommitted diff plus its report, and it dispatches nothing** (`docs/architecture.md` → `## Dispatch topology`). That is what keeps every agent at depth 1, where its completion notification actually reaches the orchestrator. The **per-issue unit gate rides this stage**: each leaf runs `unitTestCmd` in its own worktree as its TDD green step and reports real output, so N unit runs are concurrent, which is the one hazard the run-start DB interview asks about. The `tests-green` hook re-checks the suite at the orchestrator's own commit (step 8), so a leaf's report is never the only evidence.

   **Leaves never call PushNotification** — confirmed absent from subagent tool registries (see issue #97 recorded decision); the orchestrator holds every park and completion fact because it runs the gates itself, and emits at Wave boundaries. **SendMessage addressing:** the orchestrator CAN send a dispatched leaf a mid-run message (delivered at its next tool-use round) — but only by addressing that leaf's own dispatched ID/name; an agent-TYPE name (e.g. `milestone-driver:implementer`) is not a reachable address, and only the session that spawned a leaf can message it.

6. **Gate each implementer return as it lands, and hand its freed slot out — there is NO Stage A barrier (#400).** Each issue's chain is independent, so the moment one leaf returns and clears the gates below, that issue is **review-ready** and step 7 dispatches its reviewer while the rest of the set is still building. Safe to unsynchronize because nothing in Stage B reads cross-issue state and every gate below is per-leaf. **Phase 1's** one remaining synchronization point is **step 9's wave-level gather**; the Wave-boundary barrier above is the Wave's other one, separate and untouched. **End the turn while waiting** — do not poll with no-op tool calls or a tight loop (each spin re-reads the orchestrator's full context for zero new information); the harness automatically re-invokes/notifies the orchestrator as each leaf completes. A long-interval background `until`-loop (checked every several minutes, not seconds) is acceptable only as a safety net against a hung leaf that never returns a completion notification, never as the primary wait mechanism.

   **The shared-slot scheduler — the ONLY place a leaf is dispatched after step 5's initial fill.** `maxParallelWorkers` (step 3) bounds **one** counter over **all** in-flight leaves: implementer, coherence, and reviewer alike. **Every leaf return frees exactly one slot, and every freed slot is filled by exactly one dispatch** — with a single carve-out, the **coherence leaf**, whose return does **not** free a slot but **hands it straight to that issue's reviewer** (step 7 pairs the two), so an issue in Stage B occupies **exactly one slot** whether or not `coherenceReviewAgent` is configured. Run this ladder on each freed slot, **top-down, first match wins**:
   1. **An already-started chain owes a re-dispatch** — this step's unit-retry re-dispatch, or step 7's review→fix re-dispatch → dispatch it. A chain already in flight finishes before a new one starts; if the counter is full when one comes due, it waits for the next freed slot and takes it ahead of rows 2 and 3.
   2. **A review-ready issue is waiting** → enter step 7 for the **oldest** one, dispatching its coherence leaf when step 7's gate actually runs one and its reviewer leaf otherwise. **Selecting an issue DEQUEUES it immediately**, before any further ladder pass, so two frees in one batch pick two *different* issues. **"Oldest" is by the order implementer leaves RETURNED** — first-returned, first-reviewed — an ordering the orchestrator observes directly as it records each completion; **not** issue number, **not** dispatch order. Ties (two returns in one notification batch) break by **ascending issue number**.
   3. **No review-ready issue is waiting, and a set issue has not been dispatched yet** → dispatch the next **implementer** leaf, in **ascending issue number**, briefed exactly as step 5 briefs one.
   4. **Nothing to dispatch. First run every per-issue tail (step 8) still owed** — for each issue whose review converged this turn and has not been tailed, since an untailed issue reaches step 9 with no commit, no PR and no park label, which is precisely the `abandoned` shape. **A tail's gates run on the main line and hold no slot, but a RED gate re-dispatches that issue's implementer leaf into its worktree (step 8's at-most-2 cap) and that leaf DOES take one** — so read the counter *after* the tails, never before. **Then** the two outcomes, which are not interchangeable: **any leaf still in flight** → **end the turn** and wait for the next completion notification. **No leaf in flight either** → the Wave's dispatch work is finished: **do NOT end the turn**, continue on the main line to step 9's gather. Only a leaf completion re-invokes the orchestrator, so ending the turn on an empty counter strands the Wave with steps 9 to 11 unrun.

   **Review-ready beats unstarted, deliberately:** a reviewer leaf is short and its return lets step 8's tail ship that issue and free the slot again, while a fresh implementer would hold a nearly-finished chain open behind a build that may run the rest of the Wave. **A park frees NO extra slot.** Every park below fires *after* that issue's leaf has already returned and already freed its one slot (the four gates and the exhausted retry loop each read a **returned** implementer's report; a step-7 park reads a **returned** reviewer's findings), so **counting a park as a second free would put N+1 leaves against a cap of N**. What a park does is **remove that issue from the review-ready queue and from row 3's candidates**, so the ladder skips it on the free its own leaf already produced. Step 4's triage park is earlier still: that issue never becomes a candidate. A park is never a wait, and one issue's park never delays another's dispatch.

   **On each completion notification, verify that leaf's report and apply `solve-issue` step 3's gates.** First check the report honors the implementer contract (least-code / reuse-first, TDD red→green observed or a `VERIFICATION (no test layer)` section, verified citations, a Decision Log, a `USER-FACING CHANGES` block, changes left uncommitted). Then apply that step's four gates for this issue: `NEW_UI_ELEMENTS: yes` with acceptance criteria silent on the element's visual/UX detail parks `needs design`; `DESTRUCTIVE_OPS: yes` with the confirm flow unspecified parks `needs decision`; a reported new dependency parks `needs decision`; an implementer `STATUS: STOPPED` parks with that gate's own label rule (`needs design`, `needs decision`, or `blocked`). Each of those parks posts its `🔴 Parked — ` comment, applies its label (plus `in progress` when the branch has commits), preserves the branch, and **drops the issue from Stage B and from the per-issue tail**. A park that returned a diff is still a park: it does not reach review, commit, push, or PR.

   **A fifth branch, and it is not a park:** an implementer `STATUS: COMPLETE` with an **empty** `FILES CHANGED` list and a clean worktree is a **no-change outcome**, meaning this issue's acceptance criteria are already satisfied by `<base>`. It is reachable by contract, not by accident: `agents/implementer.md`'s STATUS enum is `COMPLETE | STOPPED | PAUSED-FOR-APPROVAL`, and nothing in its `## Output format` requires a non-empty `FILES CHANGED`. Record it, apply **no** park label (nothing is blocked and no human must decide anything), and drop the issue from Stage B, the per-issue tail, and step 9's partition, the same way the four gates above drop theirs. **Decide it here, at the step that already reads the report, and never at step 9.** Step 9 derives terminal state from artifacts alone, and a clean worktree with zero commits is byte-identical whether the leaf finished correctly or died before writing anything: the distinction exists only in the report, which is exactly why this branch belongs at the one step whose job is reading it.

   **A red unit suite in a leaf's report: the orchestrator owns the retry loop.** The leaf ran `unitTestCmd` in its own worktree as its TDD green step (step 5), but it cannot loop on a red result. It may not start a second suite while one is running (`agents/implementer.md`'s antipatterns), and re-dispatching itself is the depth-2 shape this file exists to avoid. So the orchestrator runs the **Unit** row of `solve-issue` `### 4. Verification gates` for that issue here: re-dispatch that issue's implementer leaf into the same worktree with the failure attached, **at most 2 re-dispatches**, invoking `superpowers:verification-before-completion` on each result and reporting real output. Still red after the second re-dispatch: park **`blocked`** (`needs design` instead when the failure shows the plan is wrong), comment, preserve the branch, and drop the issue from Stage B and the per-issue tail. The `tests-green` hook at the orchestrator's own commit (step 8) is the backstop, not this loop: it blocks rather than retries, and it fires after review and version bump.

7. **Stage B: review, concurrently, from the orchestrator — entered per issue, as each becomes review-ready.** For each issue whose implementer **returned a diff and cleared step 3's gates** (step 6), run `solve-issue` step 6.1's review-and-resolve procedure against that worktree's **uncommitted** changes, **in the dispatch shape pinned below and in no other**. **This step is entered one issue at a time, from step 6's scheduler, never as a set:** an issue reviews while its siblings are still building. **Run `solve-issue` section 6's unnumbered coherence-review block first**, before the review, for each such issue: the `coherenceReviewAgent` pass, present-and-configured-or-silently-skipped and never-gating, dispatched read-only against that worktree's uncommitted diff **as `Agent(run_in_background: true)`, like every other leaf** — it is a dispatched agent, so it is a leaf and it is counted. **It and the reviewer share this issue's ONE Stage B slot** (step 6's carve-out): the coherence leaf takes the slot when row 2 picks the issue, and **on its return the orchestrator dispatches that issue's reviewer into the same slot directly, without re-entering the ladder** — the ladder never sees that return as a free, and the reviewer is never left unreachable. **The gate is `solve-issue`'s own: present AND configured**, skipping silently when either leg fails — and its default-fill leaves **configured true but present false on a fresh install**, so skipping is the ordinary case. **Whenever it skips, no coherence leaf is dispatched and none will ever return, so the slot passes STRAIGHT to the reviewer in the same turn.** Never commit a slot to a leaf that was not dispatched: that issue would wait on a hand-off that cannot fire. Naming it here is what keeps the per-issue coherence pass from being skipped on this path (`skills/solve-milestone/SKILL.md`'s opening claim that it runs per issue inside `solve-issue` section 6 stays true under parallel issue granularity).

   **The dispatch shape, pinned: exactly one reviewer leaf per issue, and nothing nested.** Dispatch **one** review subagent per issue as `Agent(run_in_background: true)`, occupying one slot of step 3's **shared** in-flight leaf counter (step 6's ladder is what issued it). The shape is the single-reviewer dispatch `superpowers:requesting-code-review` defines: one `general-purpose` subagent filled from its `code-reviewer.md` template. Brief each one with the issue's description and its acceptance criteria (the template's `DESCRIPTION` and `PLAN_OR_REQUIREMENTS`), the profile (`sourceGlobs`, `nonNegotiables`), the review effort step 4 resolved for this issue, that issue's worktree path, and the changes to review. **Name the changes as the worktree path plus `<base>`, not as a `BASE_SHA..HEAD_SHA` range:** Stage B reviews uncommitted work, which that range does not address, so the reviewer diffs the working tree against `<base>` in the worktree it was given. Each reviewer returns findings only, in the template's shape (Strengths, then Critical / Important / Minor issues each naming a ref per `skills/citation-format.md`, then its assessment), which the orchestrator folds into that issue's `## Code Review` section (`skills/output-style.md`). A reviewer edits nothing, commits nothing, and dispatches nothing. **The brief MUST also carry the same scratch-hygiene rule as the Stage A brief above.**

   **The orchestrator never dispatches an agent that itself runs `/code-review`.** That command fans out internally, so an agent running it seats every one of its reviewers at depth 2, where a completion notification never arrives and the pipeline stops mid-cycle with the work uncommitted (`docs/architecture.md` → `## Dispatch topology`). Stage B's concurrency comes from the one-reviewer-leaf-per-issue shape above and from nothing else.

   **Only the dispatch shape moved:** from inside a per-issue agent to the orchestrator, the one session whose fan-out lands at depth 1. The gate is unchanged and unconditional: an omitted review is a park trigger (`solve-issue` step 6.1, its `/code-review` gate row, and its Autonomy model), and `hooks/code-review-gate.sh` still denies a PR whose body carries no `## Code Review` section. An in-scope finding re-dispatches that issue's implementer leaf under step 6.1's own cap (at most 2 review→fix cycles, the fresh review always the last action before commit); a park-trigger finding parks that issue and drops it from the rest of Phase 1.

8. **Per-issue tail, orchestrator-run: remaining parallel-safe gates, then version bump, commit, push, PR.** **No barrier here either.** The tail runs per issue **as that issue's review converges** in step 7; it does not wait for every issue's review. An issue that clears review first ships first. With step 6's Stage A barrier removed (#400), **steps 5 to 8 are one unbroken per-issue chain**. **Already run above, do not re-run:** the unit gate (step 5, with step 6's orchestrator-owned retry loop) and the review with its resolve loop (step 7). **Run now, per issue, in its worktree:** the **static** `preflightCmd` — the lint / format / static-analysis / security-scan class only. **Deferred to the serial tail** (Phase 2): **E2E** and any **server-starting** preflight, which run once there against accumulated integrated state, where they are both more meaningful and free of the fixed-port contention a per-worktree run invites; plus a UI issue's **render capture**, which boots that same fixed-port daemon. A UI issue's parallel-safe half of `solve-issue` step 7 still runs here (open the PR, apply `needs review`), with the screenshots owed by the serial tail or the human. **Escape hatch:** a consumer can inject a per-worktree `PORT` so each worktree binds a distinct port, keeping such a gate (capture included) in this phase. Each gate keeps its own at-most-2 cap, applied where the gate runs.

   Then run `solve-issue` steps 6.2 to 6.6 in that worktree exactly as that file states them, carried over rather than restated here, so the Decision Log, the **Code Review** section, the version bump, the commit, and the push / PR-open inherit their `integrationGranularity` conditionals (`### Integration granularity` below). Every issue applies the same idempotent same-line bump to the shared `plugin.json` target, which the tail's 3-way merge reconciles without conflict. **Nothing merges here:** Phase 1 builds and does not integrate.

9. **Derive terminal state from git/gh, never from an agent's self-report — ONCE per Wave, as a gather.** A final assistant message is free text with no schema enforcement, and it reports only what an agent *believed*, so a schema on top of it would prove no more. **This step is Phase 1's one barrier, and it holds the guarantee the removed Stage A barrier used to give (#400):** run it **once**, after **every** dispatched chain for the Wave has returned — every implementer leaf and its re-dispatches, every reviewer leaf, every per-issue tail (step 8) — and **never per issue as a chain finishes**. Await those completions the way step 6 describes, ending the turn while waiting. **Load-bearing, not ceremony:** the `abandoned` legs below key on the **absence** of artifacts, which an issue still mid-build presents identically, so probing a live leaf would classify a healthy in-flight issue `abandoned` and its recover-once ladder would dispatch a **second** implementer into the worktree the first is still writing to. Gathering the whole Wave first is what makes **out-of-order completion change nothing**; the status board reports from this one gather. Then, per dispatched issue, **derive terminal state from git + gh ground truth**, exactly the way the rest of the engine already does:

   **Wave-state checkpoint — consult before probing (resume optimization, #291).** Before running the probe below for a given dispatched issue, check `.milestone-config/.runtime/wave-state.json` for that issue's entry — a persisted cache of this step's own output from a prior pass (e.g. the run was killed mid-Wave and re-invoked). This changes nothing about the probe itself; it only decides whether the probe runs at all for that issue this pass:
   - **Read, degrade-to-empty on absent/corrupt.** `jq . .milestone-config/.runtime/wave-state.json 2>/dev/null` (Bash) / the try/`ConvertFrom-Json` pattern (PowerShell) — file absent, unreadable, or invalid JSON is treated identically to "no entry for any issue": fall straight through to the unchanged probe below for every issue in the set. Mirrors `triage-cache.json`'s own degrade-to-empty read (`scripts/triage-cache.sh (lookup: degrade to an empty cache)`); fail-open, never a crash (`.project/design-philosophy.md#Error & failure philosophy`).
   - **Freshness check — trust only if not older than the artifact it names, and ONLY for `built-green` entries** (mirrors the triage cache's stale-edge trust-but-verify posture, `scripts/triage-cache.sh (check-edges: closed but not merged)`):
     - **Scope: `built-green` only — a `parked` or `abandoned` entry is NEVER trusted from the checkpoint, at any freshness.** Park/unpark is a **label change** (`gh issue edit --add-label` / `--remove-label`), not a commit — a `parked` entry checked only against a branch-commit or PR timestamp could never self-invalidate once the park is lifted (the label changes; no commit or PR update necessarily follows), so a stale `parked` entry would wrongly exclude that issue from Phase 2 **forever**, with no signal that could ever mark it stale. A `parked` entry therefore never shortcuts anything — it always falls through to the same unchanged full probe documented below (live labels plus the `🔴 Parked` / `🔴 Triage` / `🔴 Blocked` comment, the same signal this step's probe already reads), exactly as if no checkpoint entry existed for it. An `abandoned` entry is excluded for its own reason: it names the one state the recover-once ladder below exists to resolve, so trusting it from the checkpoint would skip the very recovery it should trigger. It falls through to that same full probe.
     - For a `built-green` entry, convert **both sides to epoch seconds and compare as integers** — never a raw ISO-string compare (a `Z`-suffixed UTC string and a local-offset string do not sort correctly as strings):
       - Entry's `pr` present (issue granularity, or a UI issue under wave granularity; never under `integrationGranularity: "milestone"`, where no issue has a per-issue PR, UI included — see `### Integration granularity` below): `derived_epoch=$(jq -rn --arg d "<derivedAt>" '$d | fromdateiso8601')`; `updated_epoch=$(jq -rn --arg u "$(gh pr view <pr> --json updatedAt --jq .updatedAt)" '$u | fromdateiso8601')` (confirmed valid `--json` field; `gh` always returns a `Z`-suffixed UTC timestamp, so `fromdateiso8601` applies cleanly to both sides). Fresh iff `[ "$derived_epoch" -ge "$updated_epoch" ]`.
       - Entry's `pr` absent (wave granularity, logic issue; or `integrationGranularity: "milestone"`, every issue including UI — no per-issue PR by design): `derived_epoch=$(jq -rn --arg d "<derivedAt>" '$d | fromdateiso8601')`; `branch_epoch=$(git for-each-ref --format='%(committerdate:unix)' "refs/heads/<branch>")` against the entry's own **concrete** `branch` field — `committerdate:unix` is already epoch, so no jq conversion is needed on that side. Fresh iff `[ "$derived_epoch" -ge "$branch_epoch" ]`. **Never** a bare glob revision — `git log -1 --format=%cI 'issue/<n>-*'` is not a valid `git log` revision and silently returns empty output at exit 0 (verified); `for-each-ref` against the entry's stored concrete branch name is the form that works, and needs no glob at all since the branch name is already known. **If `for-each-ref` itself returns empty** (the branch was deleted, e.g. already merged-and-pruned since the entry was captured) → treat the entry as **stale** exactly like a missing one: fall through to the full live re-probe for that issue (fail-open, the same posture as every other degrade path here).
     - Fresh (`derived_epoch -ge` the reference epoch, entry is `built-green`) → **trust the entry directly**: use its `{issue, wave, status, branch, pr, isUI}` in place of running the probe for that issue. This is a **checkable predicate** (epoch against a named artifact), not a self-report, which is why it is a sound skip.
     - Stale (entry older than the artifact, or `for-each-ref` returned empty), **any `parked` or `abandoned` entry** (never eligible for the skip — see above), or **no entry for this issue** → fall through to the unchanged probe below, exactly today's behavior.

   For every issue that falls through (no fresh checkpoint hit):
   - run the `solve-issue` **step-3 branch-state probe** against each issue's worktree branch — PR state for `issue/<n>-*` (path-a query `gh pr list --state all --limit 200 --json number,headRefName,state,url --jq '.[] | select(.headRefName | startswith("issue/<n>-"))'`; under `integrationGranularity: "milestone"` path-a matches nothing for **every** issue, which is that granularity's normal state and never means "nothing built"; path-b and the trailer carry the signal there), commits ahead of `<base>` (path-b, `git rev-list --count <base>..issue/<n>-<slug>`), and park state from **live labels** (`gh issue view <n> --json labels` — `needs design` / `needs decision` / `blocked`) plus the `🔴 Parked` / `🔴 Triage` / `🔴 Blocked` comment (the same signal the sequential loop reads at step 4);
   - derive `isUI` independently from `git diff <base>...HEAD --name-only` ∩ `uiSurfaceGlobs`, never from a PR's changed-file list. Under `integrationGranularity: "milestone"` `<base>` is the milestone branch, **never** `integrationBranch`: a branch cut from the milestone branch and diffed three-dot against `integrationBranch` instead reports every already-folded issue's files as this issue's own.

   **Partition the dispatched set into `built-green`, `parked`, and `abandoned` from the ground-truth derivation, not from parsing any final message. Those three are exhaustive and mutually exclusive; the first two alone are not exhaustive:**
   - **`built-green`** — the probe found an open PR for `issue/<n>-*` (probe path a), or a **pushed** branch carrying commits ahead of `<base>`, **and** no park label. **Pushed-ness needs its own read.** Probe path b (`git rev-list --count <base>..issue/<n>-<slug>`) counts *local* commits and can never establish that anything reached `origin`, so confirm the push with `git ls-remote --heads origin issue/<n>-<slug>` (non-empty) and never infer it from a non-zero path-b count alone: an unpushed branch read as `built-green` is handed to Phase 2, whose step 2 runs `gh pr merge --squash --delete-branch` against a PR that does not exist. Under `integrationGranularity: "milestone"` the ground truth is instead a **local** branch with commits ahead of the milestone branch, **or** its `Issue: #<n>` trailer already on that branch, since neither an open PR nor a pushed branch ever exists there. These form the green set handed to Phase 2 (branches built + pushed, per-issue PR opened in issue granularity; built only, nothing pushed and no PR, under milestone granularity).
   - **`parked`** — the probe found a park label (`needs design` / `needs decision` / `blocked`) with its `🔴 Parked` / `🔴 Triage` / `🔴 Blocked` comment. These are **excluded from the merge tail**, with their **branch, label, and comment intact**. The orchestrator does not re-park or re-label — it simply omits the issue from Phase 2, exactly as the sequential loop excludes a parked issue. For each parked issue, **emit one `⏸️ #N parked — <reason>` notification** (reason = the live label plus that comment's reason) **before emitting the aggregate 🌊 wave-boundary notification**.
   - **`abandoned`**: the probe found **neither of the two buckets above**, which is exactly what makes the partition exhaustive. Its legs are **no PR** (probe path a), **no pushed branch carrying commits ahead of `<base>`** (`git ls-remote --heads origin issue/<n>-<slug>` empty, or non-empty with a 0 path-b count), and **no park label**. Under `integrationGranularity: "milestone"`, where path a matches nothing for any issue and no branch is ever pushed, those legs resolve instead to **0 commits ahead of the milestone branch** (probe path b), **no `Issue: #<n>` trailer on that branch**, and **no park label**; the trailer leg is load-bearing, because an issue already folded onto the milestone branch whose worktree step 2 then recreated fresh (its discard-safe leg) sits at 0 commits ahead with a clean worktree and would otherwise match `built-green` and this bucket at once. This is a **named third bucket, never a fall-through**: without it, an issue in neither bucket above vanishes with no label, no comment, and no notification, and an auto-denied background leaf (`skills/solve-issue/SKILL.md (Background subagents auto-deny any)`), context exhaustion, and a killed run all produce exactly this shape. The bucket covers **three sub-shapes**, told apart by the ladder below rather than by this classifier: a worktree carrying an uncommitted diff; a worktree carrying none (the leaf died before writing anything, so recovery starts from zero); and a branch already carrying **local commits ahead of `<base>` that were never pushed**, the state a run interrupted inside step 8's commit-then-push seam leaves behind, which step 2's carries-work leg and `solve-issue`'s resume path (b) both already treat as first-class. Read the worktree with `git -C .milestone-config/worktrees/issue-<n> status --porcelain` (a path that does not exist reads as **no** uncommitted work, and the ladder recreates the worktree per step 2 before dispatching). **Do not park it on sight.** Park asserts a human must decide something; here nothing is known to be wrong, the runtime dropped the baton, so parking would assert a design gap that does not exist, and `skills/solve-milestone/SKILL.md (no blocker label)`'s buildability condition (b) would then block the rebuild until a human clears the label, discarding gate-passing work to file a ticket saying the harness hiccuped. Resolve it with the recover-once ladder below, **inside this same pass**, so every dispatched issue leaves step 9 as `built-green` or `parked`.

   **Recover an `abandoned` issue exactly once, then park (cap 1).** **Check the branch first.** When it **already carries commits ahead of `<base>`** (probe path b, non-zero), the implementation is present and there is nothing to dispatch: **skip the recovery leaf entirely** and re-run the orchestrator's own Stage B review (step 7) and per-issue tail (step 8) for that issue, which is precisely where the interrupted commit-then-push seam left off. Otherwise dispatch **ONE** `implementerAgent` leaf into that issue's **existing worktree** as `Agent(run_in_background: true)`, **no more than `maxParallelWorkers` LEAVES in flight at once across the whole abandoned set** (step 3's same cap; step 6's ladder does not run here, because every Stage A/B chain has already returned). **The cap counts every leaf this ladder causes, not the recovery leaves alone, and the refill trigger is a SLOT FREEING, never a recovery leaf returning:** a returning recovery leaf **HOLDS its slot** for the step-7 leaf its resume dispatches (the carve-out shape step 6 uses), and the skip-the-recovery-leaf branch above **takes a slot from the same cap** before dispatching its step-7 leaf. The slot frees when that **step-7** leaf returns, and **that** is when the next abandoned issue is dispatched, so a set wider than the cap still drains. Brief the recovery leaf exactly as step 5 briefs an implementer leaf (including the **expected file scope** and the **`risk:light` token** when step 4 resolved this issue's build profile to light, both of which step 5 requires and neither of which this ladder may drop), plus an **implementation-only finish-list** naming what is left to build. **Scope that finish-list to implementation only:** it must not name step 8's tail (version bump, commit, push, PR), because a dispatched agent is a leaf that returns an uncommitted diff and dispatches nothing (step 5). **The leaf dispatches nothing, and the cap is 1, not 2** (unlike step 6's unit-retry loop): this is a dropped baton, not a non-converging loop.

   When it returns, confirm from **ground truth, never from its report**, that the worktree now carries an uncommitted diff (`git -C .milestone-config/worktrees/issue-<n> status --porcelain` non-empty), then resume the orchestrator's own Stage B review (step 7) and per-issue tail (step 8) for that issue, exactly the way step 6's re-dispatch already hands back; this step then re-derives that issue's terminal state after step 8, as it does for every other issue. **Do not re-run the partition above at this point.** A leaf that has just returned holds an uncommitted diff and zero commits, which is this bucket's own shape, so re-partitioning here would classify a **successful** recovery as `abandoned` a second time with its cap already spent.

   **Recovery fails, the diff confirmation still finds nothing, or a gate comes back red** → park **`blocked`**, post its `🔴 Parked — ` comment in `skills/output-style.md`'s park-comment shape, whose **evidence** slot names the stage the issue was abandoned at (the stage it was last dispatched into) plus the probe output that classified it, **preserve both the branch and the worktree** (step 10's cleanup carves this park out of its remove-on-park trigger), drop the issue from Stage B, the per-issue tail, and Phase 2, and **let the Wave continue**. `blocked` is the label: `needs design` and `needs decision` each assert a gap that has not been shown to exist.

   **Wave-state checkpoint — write after deriving (#291).** Immediately after this step's terminal state is established for a dispatched issue — whether freshly derived by the probe just now, or already trusted from a fresh checkpoint entry above — write/update that issue's entry in `.milestone-config/.runtime/wave-state.json`. Per issue, immediately, not batched to Wave end (mirrors `triage-cache.json`'s own read-modify-write discipline, `skills/triage/SKILL.md` Step 6.5):

   ```json
   {
     "<issue_number>": {
       "issue": <n>,
       "wave": <N>,
       "status": "built-green" | "parked" | "abandoned",
       "branch": "issue/<n>-<slug>",
       "pr": "<PR URL>" | null,
       "isUI": true | false,
       "derivedAt": "<ISO 8601 UTC timestamp of this derivation, e.g. via `date -u +%Y-%m-%dT%H:%M:%SZ`>"
     }
   }
   ```

   - **`branch` is always required** — it is the freshness anchor for the wave-granularity and milestone-granularity no-per-issue-PR cases above, and it is the one field the probe cannot re-glob for after the fact.
   - **`pr`** is the PR URL when a per-issue PR exists (issue granularity, or a UI issue under wave granularity); `null` for a `parked` or `abandoned` entry, a `built-green` logic entry under wave granularity, or **any** entry under `integrationGranularity: "milestone"`, UI included (no per-issue PR by design).
   - **`"abandoned"` is a defensive enum value this step never writes.** The recover-once ladder above resolves every `abandoned` classification to `built-green` or `parked` inside this same pass, before this write fires, so no specified path persists it. It is in the enum, and in the never-trust scope above, so that an entry written by hand or by a future path never shortcuts: like `parked`, it always falls through to the full probe. A run killed mid-recovery needs no entry of its own, because a missing entry already falls through to that same probe.
   - **Write mechanics mirror `triage-cache.json` verbatim** (`skills/triage/SKILL.md` Step 6.5): `mkdir -p .milestone-config/.runtime` first (no writer may assume the directory exists), then merge this issue's entry into the existing object keyed by issue number — `jq --arg n "<n>" --argjson entry '<entry-json>' '.[$n] = $entry'` read via a temp file and `mv`'d into place (Bash), or `ConvertTo-Json -Depth 10` + `Set-Content -Encoding utf8NoBOM` (PowerShell) — no external-tool dependency on that path.
   - **Best-effort, fail-open.** A write failure (permissions, disk, concurrent-run collision) logs one line and continues the run; the file is a resumability optimization, never the source of truth, so its loss never blocks or crashes the barrier (`.project/design-philosophy.md#Error & failure philosophy`).
   - **No new gitignore entry needed.** `.milestone-config/.runtime/` is already listed in the committed `.milestone-config/.gitignore` and in `.project/environment.md#Data stores`; `wave-state.json` inherits the ignore as-is.

10. **Cleanup the fleet.** The orchestrator removes a worktree once it is integrated by Phase 2, **or** its issue parked (**except** an issue parked by step 9's recover-once ladder, whose worktree is preserved until Wave end / run end so the recovery evidence that park's comment cites survives for a human to read), **or** at Wave end / run end:

   ```
   git worktree remove .milestone-config/worktrees/issue-<n>
   ```

   A built-green issue's branch was already **pushed** at step 8 (and, in issue granularity, has a PR open), so its **local worktree is safe to remove at Wave end / run end regardless of Phase 2** — the work is preserved on the remote branch / PR, not in the local worktree. **Under `integrationGranularity: "milestone"` the basis is local and the removal behavior is unchanged:** an integrated branch's work lives in its squash commit on the milestone branch (`milestone-granularity.md § Folding an issue into the milestone branch`), and a built-green branch not yet folded keeps its commits because `git worktree remove` deletes the checkout directory, not the branch, so step 2's carries-work leg resumes them next run. Removing at Wave end / run end (rather than gating cleanup on Phase 2) prevents built-green worktrees from being orphaned, and — together with step 2's pre-clean guard — keeps the next parallel run collision-free. Run `git worktree prune` **best-effort** at Wave end, at run end, and on systemic failure, to clear any stale fleet entries. The scratch dir `.milestone-config/worktrees/` is gitignored, so the fleet never pollutes the working tree or a commit. (A leftover old-named `.milestone-driver-worktrees/` dir in an existing clone is harmless: it is gitignored and simply unused by the new path.)

11. **Hand the green set to Phase 2, and emit one cost record per Wave.** `solve-issue`'s `## Run-end cost record` fires at a terminal exit that returns to a caller, and this per-issue tail never returns to one, so **Phase 1 emits one record per Wave, not one per issue**: aggregate every dispatch this Wave made (each implementer leaf including its re-dispatches, each reviewer leaf, any coherence pass) into a single record keyed by the Wave and emit it here, following that section's own aggregate / map / emit steps unchanged. Additive and never-gating, exactly as that section states. The `built-green` set is held (branches built + pushed; built only, nothing pushed, under `integrationGranularity: "milestone"`) and integrated by **Phase 2 — the serial verified merge tail (#73)**. The split is explicit: **Phase 1 = a pipelined per-issue build → review → tail chain, gathered once at step 9; Phase 2 (#73) = the serial verified merge tail below.** Phase 1 performs **no merge to `integrationBranch`** (and none to the milestone branch under milestone granularity, the target Phase 2 folds onto there): it builds and does not integrate, and the green set waits for Phase 2.

**Blast-radius boundary unchanged.** As in sequential mode, Phase 1 and the serial tail merge only to `integrationBranch`, **never** `protectedBranch`. Under `integrationGranularity: "milestone"` the immediate target is the milestone branch, which reaches `integrationBranch` only through the single milestone-end PR (`milestone-granularity.md`); `protectedBranch` is untouched either way.

### Parallel mode — Phase 2: serial verified merge tail

This subsection applies **only** when the run resolved to **parallel** mode (see the *Resolve execution mode* Before-starting step). It runs **after** Phase 1, consuming the `built-green` set Phase 1 derived. **Phase 2 runs to completion at the end of each Wave, before the next Wave's Phase 1 step 1 cuts its worktree fleet from the same target** (Phase 1's Wave-loop preamble states this guarantee in full). **Parked** issues are excluded — Phase 1 already omitted them, with branch + label + comment intact. **UI built-green issues are also NOT merged here** — they are held open with the `needs review` label (the Layer-2 visual gate, `solve-issue` step 7, unchanged). The tail integrates **only the non-UI built-green branches**. **Under `integrationGranularity: "milestone"` the tail integrates every built-green branch, UI included:** there is no per-issue PR for the hold to attach to, so a UI branch excluded here would have no integration path at all, and the hold moves up one level to the single milestone PR's `visualHold` gate (#376, `docs/profile-schema.md (Should the single milestone PR wait)`).

**Run on the main working tree** (not in a worktree), over the built-green non-UI branches in **ascending-issue order** (every built-green branch, UI included, under `integrationGranularity: "milestone"`). **Force-free by default (merge-in — no history rewrite).** The **integration target advances after each merge**, so two same-Wave siblings that touch overlapping files are re-verified against each other — restoring the "every increment tested against accumulated state" guarantee that naive concurrent merging throws away. For each such branch:

1. **Merge the integration target INTO the issue branch.** `git fetch`, then `git merge <target>` where `<target>` is `integrationBranch` in issue granularity, or the **wave branch** in wave granularity (#75; see `### Integration granularity (issue vs wave)` below). This brings accumulated state onto the issue branch as an ordinary merge commit — a **fast-forwardable** push, **no `--force`**. **Under `integrationGranularity: "milestone"` `<target>` is the milestone branch**, and the fold runs there rather than onto the issue branch, per `milestone-granularity.md § Folding an issue into the milestone branch`: that file owns the mechanics (squash-merge the issue branch onto the target, re-verify against the staged state, commit with the `Issue: #<n>` trailer) and is not restated here; steps 2 to 4 below read against it as noted.
2. **Clean merge** → push (fast-forward) → **re-verify against accumulated state**: run `unitTestCmd` if defined, **plus the E2E / port-binding gates Phase 1 deferred** (its step 8) — run **once here against accumulated integrated state**, where they are more meaningful. **Under wave granularity, run the read-only post-build coherence pass here too** (`coherenceReviewAgent`, present-and-configured-or-silently-skipped, never-gating) — the assembled wave is the largest body reviewed before its one wave PR, so this is the wave-granularity analogue of `solve-issue` section 6's per-issue pass. On green → `gh pr merge --squash --delete-branch` → re-sync local `integrationBranch` (`git fetch`, fast-forward). The `--squash` collapses the merge-in commit so the integration target's history stays linear. **Under `integrationGranularity: "milestone"` the push, the `gh pr merge --squash --delete-branch`, and the re-sync do not run, unconditionally**: no profile key and no conditional enables any of them, because nothing reaches origin before milestone end (`milestone-granularity.md § Branch model`). On green there, integrate with the local squash-merge-plus-one-commit that file defines; its `Issue: #<n>` trailer is what the buildability and resume reads above resolve against. The wave-granularity coherence-pass clause stays wave-scoped: under milestone granularity the largest body reviewed before one PR is the whole milestone, so that analogue belongs to the milestone-end sequence (#371), not here.
3. **Conflict** → **bounded auto-resolve**: attempt resolution with full-milestone context (git's `ort` strategy already auto-resolves **non-adjacent** same-file edits — e.g. two siblings editing separate regions of the same file), then re-verify. **Two edits on directly adjacent lines conflict**, so a file with one shared append point (a changelog table, a barrel export, a DI registration list) conflicts by construction under concurrency. **That shape is *within* bounded auto-resolve, not a park trigger:** both hunks are additive and order is not semantically load-bearing. Park stays for genuinely ambiguous semantics, a conflict still non-trivial after the attempt, or a red re-verify. **Do not recommend `merge=union`** as the fix in a park comment: it never reports a conflict, so it removes the only signal you would get, and it interleaves multi-line changes into structurally broken output (a row landing below the trailing bullets, orphaned from its table). **Resolvable AND green** → proceed to step 2's merge. **Non-trivial / ambiguous OR red** → `git merge --abort`, **park `blocked`** (comment + label + preserve branch), continue with the next branch. **Under `integrationGranularity: "milestone"` the park is identical but the recovery command is not:** `git merge --squash` writes no `MERGE_HEAD`, so `git merge --abort` fails there with `fatal: There is no merge to abort (MERGE_HEAD missing).` and the recovery is `git restore --staged --worktree .`, run on **both** park paths (step 4 included) before the next branch, per `milestone-granularity.md § Folding an issue into the milestone branch`. Do not substitute `git reset --hard`, which consumer destructive-command hooks routinely block by pattern.
4. **Clean merge but red re-verify** → **park `blocked`** (the combination is broken; a human decides), continue with the next branch.

**Why merge-in, not rebase + force (field-found).** A history-rewriting push is fragile across consumer safety setups: in a real run, `--force-with-lease` (and the delete-then-fresh-push fallback) were **BLOCKED** by two independent guards — a consumer destructive-command hook that treats the safe `--force-with-lease` like a raw `--force`, and the runtime's destructive-action classifier. A `no-push` hook permitting the push is **necessary but not sufficient** when those other guards stand. **Merge-in gives the identical re-verify guarantee with no history rewrite**, so it is the default. The **rebase + `--force-with-lease` variant stays available** as the allow-list-required alternative — but it **MUST be allow-listed** in the consumer's hooks / destructive-action classifier first.

**Wave-boundary notification.** After Phase 2 completes for a Wave (all built-green non-UI branches merged, UI PRs held open, parked issues excluded; under `integrationGranularity: "milestone"` every built-green branch folded onto the milestone branch, UI included, and no per-issue PR held) and before the next Wave's Phase 1 begins, emit a `PushNotification` — **only when another Wave follows** (🌊 is suppressed on the final Wave; the 🏁 run-complete notification is the single end signal):
```
🌊 Wave N done · X/Y ✅ · next: Wave N+1
```
Where N = the just-completed Wave number, X = issues merged this Wave (non-UI built-green, by Phase 2; under `integrationGranularity: "milestone"` every built-green issue squash-merged onto the milestone branch, UI included), Y = total issues in this Wave (all outcomes: merged + parked + triage-parked), next = Wave N+1 number. Parked-wave notifications (Class 1, per-issue) are already emitted individually as each park occurs; this wave-boundary notification covers the Wave's aggregate result.

### Integration granularity (issue vs wave)

`integrationGranularity: "issue" | "wave" | "milestone"`, default `"issue"` (`docs/profile-schema.md (How should built issues integrate?)`). This controls **how built issues integrate**, and is **orthogonal to the parallel/sequential execution mode** (which controls *how* issues build). The two combine or apply independently: any of {sequential, parallel} × {`"issue"`, `"wave"`, `"milestone"`} is valid.

**`"issue"` (default).** Each built issue opens **its own PR** → its own CI run → merges individually: in sequential mode each issue's `solve-issue` opens and merges its own PR; in parallel mode the Phase 2 serial verified merge tail merges each built-green PR in turn.

**`"wave"`.** The merge-tail **MECHANISM is unchanged** (merge-in + re-verify against accumulated state + bounded auto-resolve, #73); only the **target** and **PR-opening** differ:

- **No per-issue PR.** Phase 1's per-issue tail (step 8) builds, verifies, commits, and pushes each issue branch but opens **no per-issue PR**: `solve-issue` step 6.6 is already granularity-conditional, and wave granularity is one of the values that suppresses it. The wave-state entry for such an issue carries `pr: null`.
- **Integrate into a wave branch.** The orchestrator integrates the Wave's built-green **logic** branches into a **wave branch** `wave/<milestone>-w<N>` (N = the Wave number). **Create the wave branch fresh and idempotently:** unlike the per-issue `issue/<n>-<slug>` branches — which may carry **unpushed** commits that Phase 1's resume-aware pre-clean guard must preserve-don't-clobber (step 2) — the wave branch is a **regenerable integration artifact**, assembled entirely from the already-pushed per-issue logic branches, so it carries no unique unpushed work and is **safe to force-clear and rebuild** on every run. Before creating it, if a stale leftover exists from an interrupted prior run, delete it (`git branch -D wave/<milestone>-w<N>` locally; `git push origin --delete wave/<milestone>-w<N>` if it was pushed) and recreate it fresh from the current `integrationBranch` tip — no preserve concern, because the source work lives on the pushed per-issue logic branches. This keeps the wave path re-runnable, consistent with Phase 1's fleet idempotency. Then apply the **#73 policy unchanged**: merge each branch into the wave branch, re-verify against accumulated state (unit + deferred E2E / port-binding gates), bounded auto-resolve on conflict, else park `blocked` (label + comment + preserve branch) and continue with the next branch. The integration target is the wave branch, so siblings are re-verified against each other exactly as in the per-issue tail.
- **One wave PR.** The orchestrator opens **one wave PR** → `integrationBranch` whose body lists the Wave's logic issues in the wave-PR-body shape (`skills/output-style.md`): one line per logic issue, its **evidence slot** naming that issue's branch and the gates it passed on the wave branch (an issue listed with no branch or gate record is an unfilled slot). On **CI green**, it **squash-merges** the wave PR. A repo with **no required checks (no CI)** is **vacuously green** — proceed to squash-merge immediately, exactly as the per-issue path does (with no required status checks to gate on, `gh pr merge --squash` is mergeable; same behavior the per-issue auto-merge relies on, `solve-issue` step 8). Auto-merge-on-green moves from per-issue to **per-wave** — the whole assembled Wave merges on one green CI run.
- **Explicit issue close (do NOT rely on the `Closes #…` keyword).** A GitHub `Closes #n` keyword auto-closes an issue only when the PR merges into the repository's **default** branch. The wave PR targets `integrationBranch`, which is typically **not** the default branch (e.g. `develop` vs `main`), so the keyword would **not** fire. Therefore, after the wave PR squash-merges, the **orchestrator explicitly closes the Wave's logic issues** — `gh issue close #a #b #c --reason completed` — exactly as the per-issue path closes issues as a separate explicit action (the orchestrator merges and closes). If `integrations.trello` is present and a card handle was resolved, tick the checklist items for all logic issues just closed per `trello-sync.md § Wave granularity` (under `## Loop hooks`; best-effort per item; failure logged, loop continues). The wave PR body may still list the issues for traceability, but the close is the explicit `gh issue close` step, never the keyword.
- **Wave-branch disposition + re-sync.** After the wave PR squash-merges, **delete the wave branch** (`gh pr merge --squash --delete-branch`, plus `git branch -D wave/<milestone>-w<N>` locally if a local copy remains) and **re-sync the local `integrationBranch`** (`git fetch`, fast-forward) **before the next Wave** — consistent with the per-issue tail's `--delete-branch` + re-sync (Phase 2 step 2).

**Logic-only carve-out.** The Layer-2 visual gate is per-UI-issue, so a single wave PR cannot both auto-merge (logic) and hold open (UI). A Wave containing UI issues keeps those **per-issue / held**: each UI issue gets its own PR with the `needs review` label at Phase 1 step 8 (issue-granularity handling for that issue, held open for human visual sign-off), and **only the logic issues join the wave branch**. The wave PR's explicit-close list scopes **only the logic issues that actually joined the wave branch** — never the held UI issues.

**All-UI wave.** A Wave whose **entire** built-green set is UI issues opens **no wave branch and no wave PR** — every issue is held per-issue for visual sign-off, and there is nothing to integrate at the wave level.

**Trade-off.** **One red wave-PR CI blocks the whole Wave** — acceptable because the strong local gates (unit + static preflight + `/code-review` + the tail's re-verify) catch most failures **before** CI; CI is the backstop. **Not** for repos with weak local gates.

**`"milestone"`.** The merge-tail **MECHANISM is unchanged** (merge-in + re-verify against accumulated state + bounded auto-resolve, #73); only the **target**, the **on-green action**, and the level the **visual gate** sits at differ. The mechanics are `milestone-granularity.md`'s and are **not** restated here or in core `SKILL.md`; this bullet is the pointer:

- **Nothing is pushed, and no per-issue PR is opened for any issue, UI included.** Phase 1 builds, verifies, and commits on `issue/<n>-<slug>` branches cut from the milestone branch `milestone-<number>-<slug>`; Phase 2 folds each built-green branch onto that branch with the local squash-merge-plus-one-commit of `milestone-granularity.md § Folding an issue into the milestone branch`, whose `Issue: #<n>` trailer answers every resume and buildability read (`§ Resume and buildability from the trailer`). The same two sections serve the sequential loop's local merge, so nothing here is parallel-mode-exclusive.
- **One push, one PR, one CI run at milestone end** (#371), and the per-issue visual gate collapses into that PR's `visualHold` decision (#376, `docs/profile-schema.md (Should the single milestone PR wait)`) rather than a `needs review` label on a per-issue PR that never exists.
